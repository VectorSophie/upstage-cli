# upstage-cli 3.3.0 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to execute Section 3's task list task-by-task. Each Task is the unit of work; break it into TDD steps at execution time via `superpowers:test-driven-development`.

**Goal:** Ship upstage-cli 3.3.0 under the theme "see it, run it, prove it" — promote the eval harness's already-correct Docker sandbox into the main agent's execution path, add minimal native browser verification (CDP-based, no Playwright/Puppeteer dependency), give every verification stage a shared evidence store instead of inlining blobs into session JSON, and wire an optional, non-blocking vision sidecar for interpreting screenshot evidence.

**Architecture:** One new `src/runtime/artifacts.mjs` evidence store used by all three producers (Docker run metadata, browser console/screenshot capture, vision sidecar I/O). A shared executor shape (`exec(cmd, args, {cwd,env,timeoutMs}) → {stdout,stderr,exitCode}`) implemented by both the existing local path and a promoted `DockerSandbox`. A new `src/browser/` subsystem speaking raw CDP over `WebSocket`. Model-layer changes are additive only (new capability fields, one new adapter default) — no rewrite of existing adapters' message handling.

**Tech Stack:** unchanged — Bun-first ESM, zero new runtime dependencies (CDP over built-in `WebSocket`, no Playwright/Puppeteer), Node's built-in test runner.

**Full design rationale:** see `docs/superpowers/specs/2026-09-19-3.3.0-verification-evidence-design.md` — this plan is the task breakdown of that doc, not a restatement of its reasoning.

---

## 1. Release Thesis

> **See it, run it, prove it — verification produces evidence, not just a pass/fail line.**

Explicitly **not** the 3.3 thesis: ACP, a Playwright/Puppeteer dependency, remote/cloud execution backends, persistent browser profiles, or a shipped vision *agent* (the sidecar is a single bounded tool call, not a second autonomous loop).

## 2. Pre-flight (confirmed already true — do not re-derive)

- 3.2.0 tree is clean, 859/859 tests pass, `npm run check` clean (verified 2026-09-19).
- `harness/src/sandbox/docker.mjs` already has correct security defaults
  (`--network none`, `--memory`/`--cpus` caps, `--read-only` + scoped `tmpfs`,
  `--rm`) and its own passing test (`harness/tests/h6-sandbox-docker.test.mjs`)
  — thread B promotes this, it does not redesign it.
- MCP client (`src/tools/mcp/*.mjs`) is already on protocol `2026-07-28`
  (current) and already supports arbitrary stdio servers via `.mcp.json` —
  `chrome-devtools-mcp` needs zero client-side code, only documentation/optional
  init-template wiring (Task C.6).
- Model layer (`model-capabilities.mjs`, `GeminiAdapter`) has no modality
  concept and Gemini defaults to the stale `gemini-2.0-flash` — thread D
  starts from here.
- `session.mjs`'s `toolResults`/`appliedPatches` are capped JSON arrays with
  no artifact concept — thread A is genuinely new infrastructure, not exposure
  of something that already exists (contrast with most of 3.2's scope).

## 3. Task List

### Thread A — Evidence store (P0, do first; B/C/D all depend on it)

**Task A.1 — `src/runtime/artifacts.mjs` — DONE (Session 1, 2026-09-19)**
- `writeArtifact(sessionId, { kind, ext, data }) → { path, hash, kind, bytes }`,
  content-addressed by sha256, written under
  `sessionRoot()/<sessionId>/artifacts/<kind>/<hash>.<ext>` (kind-subdirectory
  added beyond the original design note, so identical bytes for different
  kinds never collide).
- `kind` restricted to a fixed union: `screenshot | console-log | network-log
  | docker-log | vision-response`. Unknown kind throws.
- `sessionRoot()` exported from `session.mjs` (was private) so `artifacts.mjs`
  doesn't duplicate the path-resolution logic.
- `resetSession()` now also removes `sessionRoot()/<id>/` (the artifacts
  directory) — this didn't exist before 3.3 since session storage was a flat
  `<id>.json` file with no per-session directory; without this fix artifacts
  would silently outlive the session that produced them.
- Tests: `tests/m35-artifact-store.test.mjs` (7 tests) — dedup by content
  hash, kind-subdirectory isolation, unknown-kind rejection, `resetSession`
  cleanup, `readArtifact` round-trip.

**Task A.2 — Session export redaction integration — DEFERRED (2026-09-19)**
- Status: not built in Session 1. Rationale: `writeArtifact`'s return shape
  (`{path, hash, kind, bytes}`) is metadata-only by construction — there are
  no raw bytes in `toolResults` to redact, so the "don't leak the file
  itself" concern this task was written for doesn't yet apply to anything.
  Zero producers exist yet (browser/Docker tools land in Sessions 2–3), so
  there's no real `toolResults` shape to build `--include-artifacts`
  embedding against — doing it now would mean guessing the convention.
  Revisit once Session 2 or 3 lands a real producer and the actual field
  shape it puts in `toolResults` is known; see the `ponytail:` note in
  `src/runtime/artifacts.mjs`.

### Thread B — Docker-backed execution (opt-in, fail-closed) — DONE (Session 2, 2026-09-19)

**Task B.1 — Shared executor interface — DONE, as a shape not a class**
- No separate `local-executor.mjs` was added — `exec.mjs`'s existing
  `runSandboxedProcess`/`runSandboxedCommand` already are the local
  executor and already returned the shared shape
  (`{ok, code, stdout, stderr, truncated, timedOut}`); wrapping them in a
  second file would have been a no-op indirection. `docker-executor.mjs`'s
  `DockerExecutor.exec()` conforms to that same shape instead.

**Task B.2 — Promote `DockerSandbox` — DONE, as a shared flag builder, not a moved class**
- Deviation from the plan's literal wording, decided during implementation
  per the plan's own "decide at implementation time" allowance:
  `harness/src/sandbox/docker.mjs`'s `DockerSandbox` is SWE-bench-task-shaped
  (`setup(workdir)` builds a per-task env image via a generated Dockerfile +
  a full workdir copy into the build context) — that fits a benchmark run,
  not an interactive agent re-running `run_shell` against files already on
  disk. Moving the class verbatim would have forced the main CLI through
  harness-specific task/image-build machinery it doesn't need.
- What actually mattered — the security posture — is shared for real:
  `src/sandbox/docker-flags.mjs`'s `buildDockerRunArgs()` builds the
  `--network none`/`--read-only`/`--tmpfs`/resource-cap flags, and BOTH
  `harness/src/sandbox/docker.mjs`'s `DockerSandbox.exec()` and the new
  `src/sandbox/docker-executor.mjs`'s `DockerExecutor.exec()` call it — one
  implementation of the part that must never drift, not two.
- Tests: `tests/m36-docker-flags.test.mjs` (8 tests, no Docker required —
  pure flag-building assertions), `tests/m37-docker-executor.test.mjs` (3
  tests, live-Docker-gated). `harness/tests/h6-sandbox-docker.test.mjs`
  re-run against the updated import — still green (its live-Docker
  assertions are gated the same way and were not exercised on this
  Docker-less dev box, same as before this change).

**Task B.3 — Sandbox selection + fail-closed — DONE**
- Per-tool-call `sandbox: "local"|"docker"` arg (not a top-level CLI flag —
  see note below) plus `UPSTAGE_SANDBOX=docker` env default, both read
  centrally in `exec.mjs`'s `normalizeOptions()`.
- `src/sandbox/select-executor.mjs`'s `resolveSandboxExecutor()` throws
  `DockerUnavailableError` (`code: "DOCKER_UNAVAILABLE"`) when
  `sandbox: "docker"` is requested and `DockerExecutor.isAvailable()` is
  false — no local fallback. `isAvailable` is an injectable seam so this is
  tested deterministically, not just live-gated.
- **Not built:** a top-level `upstage --sandbox docker` / `upstage run_shell
  --sandbox docker` CLI-flag surface. The `UPSTAGE_SANDBOX` env var already
  gives a global default, and the tool-arg is what the agent itself actually
  uses when calling `run_verification({sandbox:"docker"})` — a CLI flag on
  top is a small, independent addition or Session 5 could add it, not a
  logically-required part of B.3.
- Tests: `tests/m38-sandbox-selection.test.mjs` (7 tests) — resolution for
  local/docker-available/docker-unavailable (injected), end-to-end
  fail-closed through `runSandboxedProcess` (gated on this machine's real
  Docker absence), `UPSTAGE_SANDBOX` env default + explicit-arg override.

**Task B.4 — Wire call sites — DONE**
- `run-shell.mjs`, `run-tests.mjs`, `run-linter.mjs`, `run-typecheck.mjs` all
  accept `args.sandbox` and forward it (plus `context.session?.id` as
  `sessionId`) into `exec.mjs`. `run-verification.mjs` forwards `args.sandbox`
  into each delegated stage's `executeTool` call — this is the fix for the
  exact "call site bypassing the sandbox" risk the plan flagged: before this
  change `run_verification` called `context.executeTool(stage, {}, ...)`,
  silently dropping any sandbox choice for every stage it orchestrates.
- Docker runs with a `sessionId` write `{image, network, exitCode,
  durationMs, stdout, stderr}` to the evidence store (`kind: "docker-log"`,
  Task A.1) from one place (`exec.mjs`'s docker branch) rather than
  duplicated in each of the four tools; the tool result carries only the
  `{path, hash, kind, bytes}` reference. No `sessionId` (e.g. a bare library
  call) → still runs, just skips writing evidence.
- Tests: `tests/m39-sandbox-tool-wiring.test.mjs` (6 tests, fail-closed
  propagation through all four tools + `run_verification`, live-Docker-gated
  for the docker-path assertions, one always-on local-path assertion).
  `tests/m40-docker-log-artifact.test.mjs` (2 tests, live-Docker-gated —
  could not be exercised on this Docker-less dev box; same convention as
  every other live-container assertion in this suite, e.g. `h6-sandbox-
  docker.test.mjs`).

### Thread C.1–C.3 — Native browser verification — DONE (Session 3, 2026-09-19)

This dev box has a real Chrome install (`findChrome()` locates it at the
standard Windows path) — unlike Thread B's Docker-gated tests, every test
below ran live against a real launched browser, not just a skipped stub.

**Task C.1 — `src/browser/cdp-client.mjs` — DONE**
- Domains used: `Target`, `Page`, `DOM`, `Accessibility`, `Input`, `Runtime`,
  `Log` (`Network` wasn't needed by anything in C.3's tool set — no
  `browser_network` tool was in scope; add it if/when one is).
- One browser-level `WebSocket` connection, CDP "flatten" session addressing
  (`Target.attachToTarget({flatten:true})`) rather than a second connection
  per page target — simpler given this client only ever drives one page.
- `click`/`type` deviate from pure `Input`-event simulation for the *targeting*
  half: an element is focused via `DOM.resolveNode` + `Runtime.callFunctionOn`
  (`.focus()`), then `click` computes its box-model center (`DOM.getBoxModel`)
  and dispatches real `Input.dispatchMouseEvent` press/release, and `type`
  uses `Input.insertText` (not raw per-character key events) — this is the
  same approach Chrome DevTools MCP itself uses and is robust for
  React-controlled inputs, which raw JS `.value =` assignment is not.
- Test: `tests/m42-cdp-client.test.mjs` (5 tests, all ran live) — full
  launch→navigate→snapshot→close lifecycle, `click()` actually changes page
  state, `type()` actually fills an input (verified via `evaluate()`),
  `consoleLogs()` captures real console output, `screenshot()` returns valid
  PNG bytes (magic-byte checked). Fixture: `tests/fixtures/browser-fixture.html`
  (a button with a counter, a text input, a `console.log` on load).

**Task C.2 — Chrome discovery + `upstage doctor` check — DONE**
- `src/browser/discovery.mjs`'s `findChrome()`: standard per-OS install
  paths (checked first: `~/.upstage/browser/chrome[.exe]`, the Task C.4
  install location, so an explicitly-installed Chrome for Testing wins over
  a system one). Deliberately excludes a `PATH`-search fallback — nothing in
  this codebase relies on browsers being on `PATH`, and adding one would be
  untested surface for no current caller. Never downloads anything.
- `doctor`'s Verification section gained a "browser (Chrome)" check —
  `pass` with the resolved path, or `warn` pointing at `upstage browser

- Test: `tests/m41-browser-discovery.test.mjs` (3 tests — live discovery on

  `tests/m33-doctor.test.mjs` gained one test for the new check.

**Task C.3 — Core tools — DONE**
- `src/tools/builtin/browser-tools.mjs`: `browser_open`, `browser_snapshot`
  (accessibility tree — the only observation format, no raw-HTML escape
  hatch), `browser_click(ref)`, `browser_type(ref, text)`, `browser_console`
  (→ evidence store, `console-log`), `browser_screenshot` (→ evidence store,
  `screenshot`), `browser_close`. One file for all seven (matches this
  codebase's existing convention of grouping related tools, e.g.
  `github-tools.mjs`, `intelligence-tools.mjs`) rather than seven files.
- `src/browser/session-registry.mjs`: keeps one `CDPClient` alive per agent
  session (keyed by `context.session?.id`, `"default"` otherwise) across the
  several tool calls a verification flow makes — each tool call is a fresh
  `execute()` with no other way to carry the open browser between calls.
  `browser_open` reuses an already-open browser for the session rather than
  relaunching; `browser_close` tears it down and clears the registry entry.
  Browser state is otherwise ephemeral — a fresh `CDPClient`/user-data-dir
  per `browser_open`, no persistent profile across agent runs.
- Missing Chrome → `browser_open` throws `CHROME_NOT_FOUND` with the same
  `upstage browser install` pointer as the doctor check. Calling any other
  `browser_*` tool before `browser_open` throws `BROWSER_NOT_OPEN`.
- Registered in `src/tools/create-registry.mjs`; builtin tool count is now
  43 (was 36) — updated the count assertion in
  `tests/m33-introspection-commands.test.mjs`, `package.json`'s description,
  and `CLAUDE.md`'s tool-registry section accordingly.
- Test: `tests/m44-browser-tools.test.mjs` (3 tests, live) — full tool-level
  flow (open→snapshot→click→type→console→screenshot→close) including
  evidence-store writes for console/screenshot, plus the two error paths.

- `model-capabilities.mjs` gained `inputModalities`/`outputModalities`

**Task D.2 — Gemini adapter: default bump + image input**
- `DEFAULT_MODEL` → `gemini-3.8-flash` (was the stale `gemini-2.0-flash`).
  `toGeminiMessages` (now exported) accepts `msg.content` as either a plain
  string (unchanged) or an array of `{type:"text", text}` /
  `{type:"image", source:{type:"base64", data, mimeType}}` parts.
- **Deviation from the plan's literal wording:** only a `base64` image
  source is accepted here, not a `file`-path source. Reading a file is
  async I/O; keeping `toGeminiMessages` a pure, synchronous function (easy
  to unit-test, no I/O side effects) meant resolving a file to base64
  happens once, at the tool boundary (`inspect_image`, Task D.3) — not
  inside the adapter.
- Test: `tests/m15-providers-streaming.test.mjs` gained a block — default
  model assertion, unchanged string-content behavior, and an image-part →

**Task D.3 — `inspect_image(path, question)` tool, conditional registration**
- `src/tools/builtin/inspect-image.mjs`. `create-registry.mjs` only calls
  `registry.register(inspectImageTool)` when `isVisionSidecarConfigured()`
  (`GEMINI_API_KEY`/`GOOGLE_API_KEY` present) — no key means the tool is
  simply absent from `registry.list()`, never present-but-erroring, so
  Thread E's pipeline can treat "tool not found" as "skip this stage."
  Reads the image file, base64-encodes it, sends `{question, image}` to a
  `GeminiAdapter` (or an injected `context.__adapterOverride`, the seam the
  tests use — no real Gemini API call in this suite), writes the answer to
  the evidence store (`kind: "vision-response"`) when a `sessionId` is
  available, same optional-artifact pattern as `browser_console`/
  `browser_screenshot`.
- Test: `tests/m47-inspect-image.test.mjs` (5 tests) — configured-check
  true/false, registered/absent in a real `createRegistry()` call under
  each env state, and a mocked-adapter end-to-end execute() including the

### Thread E — Verification pipeline wiring — DONE (Session 5, 2026-09-19)

**Task E.1 — Extend `run-verification.mjs` — DONE**
- New exported pure helper `collectEvidence(results, callerEvidence)`:
  auto-pulls `docker-log` artifacts out of each stage's own result (Thread
  B), merges in whatever `args.evidence` object the agent supplies (browser/
  vision evidence it already gathered via separate `browser_console`/
  `browser_screenshot`/`inspect_image` calls earlier in the same flow), and
  the tool's result now always carries an `evidence: {...}` field — `{}`
  when nothing was configured/gathered, never an error.
- **Found and fixed a real pre-existing bug while writing this task's
  tests** (same pattern as Session 2's `run_verification`-drops-`sandbox`
  find): the per-stage loop read `result.ok` — the *registry's* "did the
  tool throw" — instead of `result.data.ok`, the stage's own reported
  pass/fail. A lint/typecheck/test stage that failed without throwing (e.g.
  a nonzero exit code, the normal way these tools report failure) was
  silently recorded as passed. Fixed to `result.ok === true &&
  result.data?.ok !== false`.
- Test: `tests/m48-verification-pipeline.test.mjs` (7 tests) —
  `collectEvidence` unit tests (empty/docker-only/merged/non-object-input),
  and full `run_verification.execute()` tests confirming the evidence field
  is always present, caller evidence is folded in, and the `ok`-field fix
  actually surfaces a real stage failure.

## 4. Testing Strategy

- No new test framework — Node's built-in `node:test`, same as today.
- Live-dependency tests (Docker, real Chrome) follow the existing harness
  pattern: gate on `isAvailable()`-style checks, never hard-fail CI when the
  dependency is absent, but must run for real when it is (matches
  `h6-sandbox-docker.test.mjs`'s existing approach — do not mock away the
  one test that proves the sandbox actually isolates).
- Target: keep the full suite green throughout (859 baseline + new tests per
  task above), `npm test`/`npm run check` clean before each task is
  considered done, matching this repo's existing bar.
