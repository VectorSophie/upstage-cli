# upstage-cli 3.3.0 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to execute Section 3's task list task-by-task. Each Task is the unit of work; break it into TDD steps at execution time via `superpowers:test-driven-development`.

**Goal:** Ship upstage-cli 3.3.0 under the theme "see it, run it, prove it" — promote the eval harness's already-correct Docker sandbox into the main agent's execution path, add minimal native browser verification (CDP-based, no Playwright/Puppeteer dependency), give every verification stage a shared evidence store instead of inlining blobs into session JSON, and wire an optional, non-blocking vision sidecar for interpreting screenshot evidence.

**Architecture:** One new `src/runtime/artifacts.mjs` evidence store used by all three producers (Docker run metadata, browser console/screenshot capture, vision sidecar I/O). A shared executor shape (`exec(cmd, args, {cwd,env,timeoutMs}) → {stdout,stderr,exitCode}`) implemented by both the existing local path and a promoted `DockerSandbox`. A new `src/browser/` subsystem speaking raw CDP over `WebSocket`. Model-layer changes are additive only (new capability fields, one new adapter default) — no rewrite of existing adapters' message handling.

**Tech Stack:** unchanged — Bun-first ESM, zero new runtime dependencies (CDP over built-in `WebSocket`, no Playwright/Puppeteer), Node's built-in test runner.

**Full design rationale:** see `docs/superpowers/specs/2026-09-19-3.3.0-verification-evidence-design.md` — this plan is the task breakdown of that doc, not a restatement of its reasoning.

---

## 1. Release Thesis

> **See it, run it, prove it — verification produces evidence, not just a pass/fail line.**

Explicitly **not** the 3.3 thesis: ACP, a Playwright/Puppeteer dependency, remote/cloud execution backends, persistent browser profiles, or a shipped vision *agent* (the sidecar is a single bounded tool call, not a second autonomous loop).

## 2. Pre-flight (confirmed already true — do not re-derive)

- 3.2.0 tree is clean, 859/859 tests pass, `npm run check` clean (verified 2026-09-19).
- `harness/src/sandbox/docker.mjs` already has correct security defaults
  (`--network none`, `--memory`/`--cpus` caps, `--read-only` + scoped `tmpfs`,
  `--rm`) and its own passing test (`harness/tests/h6-sandbox-docker.test.mjs`)
  — thread B promotes this, it does not redesign it.
- MCP client (`src/tools/mcp/*.mjs`) is already on protocol `2026-07-28`
  (current) and already supports arbitrary stdio servers via `.mcp.json` —
  `chrome-devtools-mcp` needs zero client-side code, only documentation/optional
  init-template wiring (Task C.6).
- Model layer (`model-capabilities.mjs`, `GeminiAdapter`) has no modality
  concept and Gemini defaults to the stale `gemini-2.0-flash` — thread D
  starts from here.
- `session.mjs`'s `toolResults`/`appliedPatches` are capped JSON arrays with
  no artifact concept — thread A is genuinely new infrastructure, not exposure
  of something that already exists (contrast with most of 3.2's scope).

## 3. Task List

### Thread A — Evidence store (P0, do first; B/C/D all depend on it)

**Task A.1 — `src/runtime/artifacts.mjs` — DONE (Session 1, 2026-09-19)**
- `writeArtifact(sessionId, { kind, ext, data }) → { path, hash, kind, bytes }`,
  content-addressed by sha256, written under
  `sessionRoot()/<sessionId>/artifacts/<kind>/<hash>.<ext>` (kind-subdirectory
  added beyond the original design note, so identical bytes for different
  kinds never collide).
- `kind` restricted to a fixed union: `screenshot | console-log | network-log
  | docker-log | vision-response`. Unknown kind throws.
- `sessionRoot()` exported from `session.mjs` (was private) so `artifacts.mjs`
  doesn't duplicate the path-resolution logic.
- `resetSession()` now also removes `sessionRoot()/<id>/` (the artifacts
  directory) — this didn't exist before 3.3 since session storage was a flat
  `<id>.json` file with no per-session directory; without this fix artifacts
  would silently outlive the session that produced them.
- Tests: `tests/m35-artifact-store.test.mjs` (7 tests) — dedup by content
  hash, kind-subdirectory isolation, unknown-kind rejection, `resetSession`
  cleanup, `readArtifact` round-trip.

**Task A.2 — Session export redaction integration — DEFERRED (2026-09-19)**
- Status: not built in Session 1. Rationale: `writeArtifact`'s return shape
  (`{path, hash, kind, bytes}`) is metadata-only by construction — there are
  no raw bytes in `toolResults` to redact, so the "don't leak the file
  itself" concern this task was written for doesn't yet apply to anything.
  Zero producers exist yet (browser/Docker tools land in Sessions 2–3), so
  there's no real `toolResults` shape to build `--include-artifacts`
  embedding against — doing it now would mean guessing the convention.
  Revisit once Session 2 or 3 lands a real producer and the actual field
  shape it puts in `toolResults` is known; see the `ponytail:` note in
  `src/runtime/artifacts.mjs`.

### Thread B — Docker-backed execution (opt-in, fail-closed)

**Task B.1 — Shared executor interface**
- Define the shared shape as a doc-comment + a `local-executor.mjs` that just
  wraps existing `runSandboxedProcess` unchanged (behavior-preserving refactor
  — no new tests needed beyond "existing sandbox tests still pass").

**Task B.2 — Promote `DockerSandbox`**
- Move `harness/src/sandbox/docker.mjs` to `src/sandbox/docker-executor.mjs`
  (or re-export from there if the harness's own imports are hard to safely
  change in one pass — decide at implementation time, but end state is one
  implementation, not two copies).
- Update `harness`'s own usage to import the promoted module.
- Test: re-run `harness/tests/h6-sandbox-docker.test.mjs` unchanged against
  the new location — it should not need behavior changes, only import paths.

**Task B.3 — Sandbox selection + fail-closed**
- `--sandbox docker` CLI flag / `UPSTAGE_SANDBOX=docker` env, read by the
  tools in Task B.4.
- `DOCKER_UNAVAILABLE` error path when Docker is requested but
  `DockerSandbox.isAvailable()` is false — no local fallback.
- Test: mock `isAvailable()` false + `--sandbox docker` → tool call returns
  the specific error, does not execute locally (assert no local process was
  spawned).

**Task B.4 — Wire call sites**
- Audit and update `run-shell.mjs`, `run-tests.mjs`, `run-linter.mjs`,
  `run-typecheck.mjs`, `run-verification.mjs` to go through the shared
  executor selection from B.3. This is the task most likely to surface a
  call site that was bypassing the sandbox entirely — flag and fix any found
  during audit, don't just wire the obvious ones.
- Docker runs write `{image, network, exitCode, durationMs}` +
  stdout/stderr to the evidence store (`kind: "docker-log"`) via Task A.1.
- Test: per-tool test confirming `--sandbox docker` path produces a
  `docker-log` artifact reference in the tool result.

### Thread C — Native browser verification

**Task C.1 — `src/browser/cdp-client.mjs`**
- Launch/attach via `--remote-debugging-port`, raw CDP over `WebSocket`.
  Domains: `Target`, `Page`, `DOM`, `Accessibility`, `Input`, `Runtime`,
  `Network`, `Log`.
- Test: can be unit-tested against a real locally-launched Chrome if present
  in CI (mirroring the Docker integration-test pattern — gate on availability,
  don't hard-fail CI without Chrome).

**Task C.2 — Chrome discovery + `upstage doctor` check**
- Standard per-OS path probing + `PATH`. Clear "not found, run `upstage
  browser install`" error, no silent no-op.
- `doctor` gains a Chrome-availability row, consistent with its existing
  never-hard-fail contract.

**Task C.3 — Core tools**
- `browser_open`, `browser_snapshot` (accessibility tree, default and only
  observation format), `browser_click(ref)`, `browser_type(ref, text)`,
  `browser_console` (→ evidence store, `console-log`), `browser_screenshot`
  (→ evidence store, `screenshot`), `browser_close`. Ephemeral state per
  invocation, no persistent profile.
- Test: each tool against a locally-launched Chrome pointed at a tiny local
  fixture HTML page (no network dependency).

**Task C.4 — `upstage browser install` (explicit opt-in)**
- Downloads Chrome for Testing into `~/.upstage/browser/`. Never invoked by
  any other command.
- Test: mock the download, assert placement + doctor picks it up afterward.

**Task C.5 — `.mcp.json` template offer**
- `upstage init` optionally offers a `chrome-devtools-mcp` entry (documented
  as the advanced-debugging path), same offer-don't-force pattern as its
  existing `UPSTAGE.md` generation. No new MCP client code required (already
  works per pre-flight).

### Thread D — Optional vision sidecar

**Task D.1 — Content-part types + modality metadata**
- Additive `{type:"text"}`/`{type:"image", source:{...}}` shape, used only by
  the new sidecar path — existing adapters' string-content handling is
  untouched.
- `model-capabilities.mjs`: add `inputModalities`/`outputModalities` arrays
  to existing entries (`["text"]` for all three Solar models today).
- Test: capability table returns the new fields; existing fields/tests
  unaffected.

**Task D.2 — Gemini adapter: default bump + image input**
- `DEFAULT_MODEL` → `gemini-3.8-flash`. Add image-part support to
  `toGeminiMessages` (Gemini's `inlineData`/file-part shape, translated from
  the provider-neutral parts internally — never leaked into core session
  history).
- Test: message-building test with a mixed text+image input; existing
  text-only tests unchanged.

**Task D.3 — `inspect_image(path, question)` tool, conditional registration**
- Registered in the tool registry only if a configured image-capable adapter
  exists (API key present). Resolves an evidence-store path, sends to the
  adapter, returns a text answer + writes a `vision-response` artifact.
- Test: registry test — key present → tool registered; key absent → tool
  absent (not present-but-erroring).

### Thread E — Verification pipeline wiring

**Task E.1 — Extend `run-verification.mjs`**
- Accept evidence references (docker-log, console-log, screenshot,
  vision-response) and fold into the existing pass/fail result shape as an
  `evidence: {...}` field. No new orchestration logic — the agent loop still
  calls the individual tools; this tool assembles the final bundle.
- Missing vision sidecar (Task D.3 tool absent) → pipeline proceeds without
  that field, never fails on its absence.
- Test: full pipeline test with all evidence present; degraded tests with
  each piece individually absent (no Docker, no browser, no vision key) —
  confirm graceful degradation at each step, matching current
  test-only-verification behavior when nothing new is configured.

## 4. Testing Strategy

- No new test framework — Node's built-in `node:test`, same as today.
- Live-dependency tests (Docker, real Chrome) follow the existing harness
  pattern: gate on `isAvailable()`-style checks, never hard-fail CI when the
  dependency is absent, but must run for real when it is (matches
  `h6-sandbox-docker.test.mjs`'s existing approach — do not mock away the
  one test that proves the sandbox actually isolates).
- Target: keep the full suite green throughout (859 baseline + new tests per
  task above), `npm test`/`npm run check` clean before each task is
  considered done, matching this repo's existing bar.

## 5. Session Split (budget-conscious)

Ordered by dependency, sized to fit one focused session each:

1. **Session 1 — Thread A (evidence store). DONE 2026-09-19.** Task A.1
   shipped (`src/runtime/artifacts.mjs`, `session.mjs` cleanup fix,
   `tests/m35-artifact-store.test.mjs`); Task A.2 explicitly deferred (see
   above). 866/866 tests green, `npm run check` clean.
2. **Session 2 — Thread B (Docker execution).** Mostly promotion of
   already-correct, already-tested code — should be the cheapest non-trivial
   session.
3. **Session 3 — Thread C.1–C.3 (native browser core).** The one genuinely
   new subsystem — budget the most review time here, not the most code.
4. **Session 4 — Thread C.4–C.5 (browser install + MCP template) + Thread D
   (vision sidecar).** Both are small, optional-path features layered on
   Sessions 1–3; bundling them avoids a session that's mostly plumbing.
5. **Session 5 — Thread E (pipeline wiring) + full-suite verification +
   CHANGELOG/version bump + release.** Integration session — nothing new to
   design, just wiring what Sessions 1–4 built into one coherent result and
   confirming the degraded-path tests actually degrade gracefully. Revisit
   Task A.2 here or in Session 2/3, whichever lands the first real artifact
   producer.

Each session ends with `npm test && npm run check` green before merge, per
this repo's existing bar — no session hands off a red suite to the next one.
