# upstage-cli 3.2.0 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to execute Section 12's task list task-by-task. This document is a release-level PRD/architecture plan (per the requester's explicit structure), not a step-by-step TDD script — each Task in Section 12 is the unit of work; break a Task into TDD steps at execution time using `superpowers:test-driven-development`.

**Goal:** Ship upstage-cli 3.2.0 under the theme "Upstage-native consolidation + interoperability + CLI/productization" — consolidate duplicated Upstage HTTP clients into one shared service layer, expose it through standalone shell-friendly commands (parse/ocr/extract/schema/classify/embed/groundedness), turn the hand-rolled CLI into a real installed-program experience (`upstage` → TUI by default, `doctor`, `init`, introspection namespaces, a hardened installer, a dev-link workflow), and evaluate ACP as the editor-integration answer to the currently-unconsumed bespoke bridge.

**Architecture:** One new `src/upstage/*.mjs` service layer (HTTP client + one module per Upstage capability) becomes the single implementation each of: existing agent tools, new standalone CLI commands, and new MCP server tools call into — no duplicate HTTP stacks. A new but deliberately small `src/cli/router.mjs` command table replaces the flat `parseCliArgs` switch as the entry point for ~20 new namespaced subcommands, reusing existing subsystems (`ToolRegistry`, `SkillsLoader`, `AgentLoader`, `PluginLoader`, `loadMcpServerConfigs`, `listSessions`, `loadSettings`) for introspection rather than building new stores.

**Tech Stack:** Bun-first ESM `.mjs`, zero new runtime dependencies (hand-rolled CLI router, `fetch` + existing `fetchWithRetry`), Node's built-in test runner, existing OpenTUI/`@opentui/react` TUI untouched in its rendering internals.

---

## 0. Executive Summary

upstage-cli reached 3.1.0 by making the *agent* substantially more capable (Solar Pro4 default, model-capability table, parallel tool calls, incremental indexing). 3.2.0 does not add agent capability — it turns the same codebase into a complete, installable, scriptable **Upstage platform CLI**, on top of infrastructure that (per the audit in §2) already exists in more complete form than the feature list in CLAUDE.md suggests.

Three findings drove this plan's shape more than anything in the original feature list:

1. **The Upstage HTTP surface is already triplicated and drifting.** `src/tools/builtin/read-document.mjs` and `src/tools/builtin/semantic-search.mjs` each hand-roll their own `node:https` client; `src/retriever/providers/upstage.mjs` hand-rolls a third with `fetch`; and the three disagree with each other on model names and env var names (`UPSTAGE_EMBEDDING_MODEL` vs. the undocumented `UPSTAGE_EMBED_MODEL`, `solar-embedding-1-large-*` vs. `embedding-query`, neither of which is the *current* model name — see §3). None of the three has a test. This is the concrete justification for §7.A's shared service layer — it is not a speculative "nice to have."
2. **`upstage` already launches the fullscreen TUI by default.** `chat`, `tui`, and no-command all route through the same `runInteractive()` → OpenTUI `App` (`src/cli/index.mjs:409-424`). The "make `upstage` launch the TUI" ask in §M is ~90% already true; the real work is collapsing three code paths that already do the same thing into one documented contract, not building new behavior.
3. **Most of the "new" introspection/diagnostic commands are exposure work, not new plumbing.** The tool registry already tags `source: "builtin"|"mcp"|"discovered"`; `listSessions()` already exists; `loadMcpServerConfigs()`/`connectConfiguredServers()` already isolate per-server failures; `checkProviderKeys()` already reports which provider keys are set; `isGitRepo()` already exists. `doctor`, `mcp list/status/test/show`, `tools/skills/agents/plugins list/show`, and `sessions list/show/resume/export` are CLI-surface work over existing internals, which is exactly the "Reuse before adding" principle this plan follows throughout.

The one place this plan deliberately does *not* just wire up existing plumbing is `/init` (a genuine no-op stub, §2/§4) and ACP (a genuine new protocol implementation, scoped as P2/stretch per §3's research — real but bounded scope, ~5 required methods).

## 1. Release Thesis

> **Upstage-native consolidation + interoperability + CLI/productization.**

3.1 made the agent internals capable. 3.2 makes upstage-cli behave like a complete installed program and the universal local interface to the Upstage ecosystem — usable as a coding agent, a terminal UI, a headless agent, a deterministic Upstage CLI, an MCP server/client, and an Agent-Skills provider — without becoming seven applications sharing one package name. One runtime, several thin, consistent surfaces over it.

Explicitly **not** the 3.2 thesis: more agent tools, more autonomy features, a new memory architecture, observability, or remote execution (§14).

## 2. Current Architecture Audit

*(Grounded in reading the actual implementation files listed below, not README/CLAUDE.md summaries — file:line references are exact as of the 3.1.0 tree, commit `a41b63b`.)*

### CLI
- Entry point: `src/cli/index.mjs` (588 lines). Argument parsing: `src/config/cli-args.mjs`'s `parseCliArgs()` — a 171-line hand-written positional/flag scanner, **no CLI parsing dependency** (`package.json` has zero — no commander/yargs/minimist). `argv[0]` is checked against a fixed set (`chat|ask|tui`); anything else falls through to being treated as the prompt string if it doesn't start with `-`.
- `main()` (`src/cli/index.mjs:426-588`): loads project env → settings cascade → plugin loader → MCP servers → agent/skills loaders → hook engine → tool registry → adapter → session, then branches on `args.command === "ask" || args.prompt"` (one-shot `executePrompt`, prints via `renderEvent` plain-text renderer) vs. everything else (`runInteractive`, OpenTUI).
- **No subcommand namespacing exists today** — `parseCliArgs` has a flat option list, not a tree. This is the concrete gap §W's router addresses.

### TUI
- `runInteractive()` (`src/cli/index.mjs:409-424`) always mounts the same OpenTUI `App` component (`src/ui/App.mjs`) via `createCliRenderer` + `createRoot(renderer).render(...)`, **regardless of whether the command was `chat`, `tui`, or omitted**. There is no separate "plain REPL" renderer in the interactive path — `plain-event-renderer.mjs`'s `renderEvent`/`canUseFullscreenTui`/`exitFullscreenTui` are used only for the **non-interactive** `ask`/`-p` path (`src/cli/index.mjs:220,231,255-318`) to print streamed events to stdout, and for terminal-state cleanup on fatal error when no renderer is mounted yet.
- Built with OpenTUI (`@opentui/core`+`@opentui/react` `0.5.1`) — confirmed in `package.json`, matching CLAUDE.md.
- **Conclusion:** the CLAUDE.md line "single CLI invocation routes to either an interactive TUI or a non-interactive one-shot prompt" is accurate; the *sub*-claim of a separate "chat" plain-REPL mode is not — `chat` is presently a naming synonym for the same fullscreen path as `tui`.

### Installation / packaging
- `package.json`: `bin` maps `upstage`→`src/cli/index.mjs`, `upstage-mcp`→`src/mcp/upstage-server.mjs`, `upstage-bridge`→`src/bridge/server.mjs`. `engines.bun >= 1.3.0`. Published to npm as `@jackochesstern/upstage-cli` (scoped name, not bare `upstage-cli`).
- `scripts/package-binary.mjs`: builds one `bun build --compile` standalone executable **per current host platform only** (no cross-compile — `@opentui/core`'s native addon is a per-platform optionalDependency resolved at install time, so cross-target compiles can't statically resolve it; `.github/workflows/release.yml` runs a real per-OS build matrix instead). Bundles `skills/`, tree-sitter `.wasm` grammars, and `LICENSE` alongside the binary because anything read relative to `import.meta.url`/`node_modules` at runtime (not statically imported) resolves to nothing inside `bun build --compile`'s virtual filesystem — `SkillsLoader`'s `SEARCH_DIRS` already special-cases this via `join(dirname(process.execPath), "skills")` (`src/skills/loader.mjs:29-34`).
- `scripts/install.sh` (56 lines): detects OS (`Linux|Darwin` only — explicitly rejects Windows with a message pointing at the release zip)/arch (`x64|arm64`), downloads `upstage-${platform}-${arch}.tar.gz` from `releases/latest/download/`, **unconditionally `rm -rf`s** `$UPSTAGE_INSTALL_DIR` before extracting, symlinks into `$UPSTAGE_BIN_DIR` (default `~/.local/bin`). **No** checksum verification, **no** `UPSTAGE_VERSION` pin/override, **no** existing-install detection/warning, **no** post-install smoke test, **no** atomic replace (the `rm -rf` then `mv` window is not crash-safe), PATH check is present (string match, prints an export hint) but not a robust `command -v` check.
- CI: `.github/workflows/ci.yml` + `.github/workflows/release.yml` (npm publish job added in 3.1.0 per CHANGELOG).

### Upstage API integrations
Three independent HTTP clients hitting Upstage, plus one adapter reused for a fourth call shape:
1. `src/tools/builtin/read-document.mjs` — raw `node:https`, `POST /v1/document-digitization`, hardcoded `model: "document-parse"`, `output_formats: "['markdown']"`, 20MB cap. **Zero tests.**
2. `src/tools/builtin/semantic-search.mjs` — raw `node:https`, `POST /v1/embeddings`, `BASE_MODEL = process.env.UPSTAGE_EMBEDDING_MODEL || "solar-embedding-1-large"` + `-query`/`-passage` suffix. **Zero tests.**
3. `src/retriever/providers/upstage.mjs` — `fetch`-based, `POST /v1/embeddings`, `DEFAULT_EMBED_MODEL = process.env.UPSTAGE_EMBED_MODEL || "embedding-query"` (**different env var, different model-naming convention** from #2 — confirmed by grep, `UPSTAGE_EMBED_MODEL` appears nowhere in `src/config/env.mjs`'s `ENV_SCHEMA`, i.e. it's an undocumented env var). Used by `src/retriever/index.mjs` for the repo-wide semantic index. **Zero tests** for the provider itself.
4. `src/tools/builtin/check-groundedness.mjs` — reuses `UpstageAdapter` (chat completions) with `VERIFICATION_MODEL = process.env.UPSTAGE_GROUNDEDNESS_MODEL || "solar-1-mini-answer-verification"`, parses the plain-string response (`grounded|notGrounded|notSure`). **Zero tests.** Per §3's fresh research, the current live model id is very likely `groundedness-check` (dated-snapshot resolved), not `solar-1-mini-answer-verification` — this default is a live correctness risk, not just a naming nit.
- Shared retry/usage-normalization primitive already exists and is under-used: `src/model/fetch-utils.mjs`'s `fetchWithRetry()` (429/5xx retry with exponential backoff, timeout detection) and `normalizeUsage()` are used by `UpstageAdapter` but **not** by any of the three raw-HTTP tools above — each of those has zero retry logic.
- `src/core/providers.mjs`: multi-provider registry (`upstage|openai|gemini|openrouter`) with `getProvider(model)`, `checkProviderKeys()` (already returns which of the four provider env vars are set — directly reusable for `doctor`/`auth status`).
- `src/model/model-capabilities.mjs`: per-model table (`solar-pro4|solar-pro3|solar-pro2`) driving context limit, `supportsReasoningEffort/ParallelToolCalls/ResponseFormat`. Already has provenance comments flagging some fields as unconfirmed against live Upstage docs — §3 resolves several of these.
- `src/mcp/upstage-server.mjs`: an MCP **server** exposing the upstage-cli *agent itself* as two delegatable tools (`upstage_delegate`, `upstage_ask`) — this is unrelated to document/extraction/classification/embedding/groundedness; it is the coding-agent-as-subagent surface, not a document-utility surface. `TOOLS` is a flat object (`name → {description, inputSchema, handler}`) at `src/mcp/upstage-server.mjs:169+` — trivially extensible with new entries.

### MCP
- Config/connect: `src/tools/mcp/config.mjs` — `loadMcpServerConfigs(cwd, settings)` merges `.mcp.json`'s `mcpServers` with `settings.mcpServers` (settings wins on collision), normalizes stdio (`command/args/env`) and remote (`url/headers`, `type: "http"|"sse"`) configs. `connectConfiguredServers(configs, {cwd, onLog, timeoutMs})` connects each in isolation — **a failing server is logged and skipped, never crashes the host** — and returns `{servers: [{name, client}], closeAll()}`. This is the exact primitive `upstage mcp list/status/test/show` needs; no new config-reading code required.
- Client transports: `src/tools/mcp/stdio-client.mjs`, `src/tools/mcp/http-client.mjs` (Streamable HTTP). Server direction: `src/mcp/upstage-server.mjs` (stdio JSON-RPC 2.0, protocol version `"2026-07-28"`).
- Client-manager: `src/tools/mcp/client-manager.mjs`; tool wrapping: `src/tools/mcp/mcp-tool.mjs` (tags `source: "mcp"`).

### Skills / agents / plugins
- **Skills** (`src/skills/loader.mjs`): already Agent-Skills-format compatible. `SEARCH_DIRS` = `.upstage/skills` → `.claude/skills` → package-bundled `<repo>/skills/` → `<execPath dir>/skills` (compiled-binary fallback) → `~/.upstage/skills`, first-seen-wins. Parses `SKILL.md` frontmatter (name/description/aliases/trigger/license) + body; `get()` does exact→prefix→alias matching; `run(name, args)` substitutes `$ARGUMENTS`. The repo already ships 24 first-party skills under `/skills` (Korean-market utilities: `document-ai-parsing`, `groundedness-check`, `semantic-code-search`, and 21 others) — i.e. this repo is already both a skill *consumer* and a skill *publisher* in the Claude-compatible format, which is directly relevant to §I.
- **Agents** (`src/agents/loader.mjs`, `src/agents/parser.mjs`): `SEARCH_DIRS` = `.upstage/agents` (project-local only per the grep — no `.claude/agents`/global dir seen in this loader, unlike Skills/Plugins).
- **Plugins** (`src/plugins/loader.mjs`): reads Claude-compatible `.claude-plugin/plugin.json` manifests; search dirs = `.claude/plugins`, `.upstage/plugins` (project), `~/.claude/plugins` (global). Merges plugin-provided hooks/MCP servers/agents/skills into the main loaders at startup (`src/cli/index.mjs:507-528`).
- **Hooks** (`src/hooks/engine.mjs`): `HookEngine` already implements Claude-compatible lifecycle points including `PreToolUse` (can deny with a message), `PostToolUse`, `Stop` (can prevent stop), `Notification`, `SessionStart`, `UserPromptSubmit`. Fail-open/fail-closed is configurable.
- **Discovered tools** (`src/tools/discovery/`): external-command JSON tool specs, tagged `source: "discovered"` (`src/tools/discovery/discovered-tool.mjs:11`).
- **Tool registry** (`src/tools/registry.mjs`): `ToolRegistry.register()` tags builtin tools `source: "builtin"` (`:73`); `.list()`/`.get()` support filtering by `source` (`:110`). **This three-way source tag already covers exactly what §R asks `upstage tools list` to report** — no new classification logic needed.

### Sessions
- `src/runtime/session.mjs` (272 lines): `createSession`, `forkSession`, `appendHistory/appendToolResult/appendAppliedPatch/appendRuntimeEvent`, `saveSession`, `loadSession`, **`listSessions()`** (already exists), `loadLatestSession`, `resetSession`. Events are already sanitized before persistence (`sanitizeValue()`, truncates strings >500 chars, arrays >20 items, depth >4, marks the `session` key specially to avoid storing itself recursively) — this sanitization is the right base to extend for §L's export redaction, not a new mechanism.
- Storage root: `~/.upstage-cli/sessions/` (per CLAUDE.md — distinct from the `~/.upstage/` settings root; confirmed by this audit's reading of `session.mjs`'s use of `os.homedir()` + a session-specific join, consistent with CLAUDE.md's explicit callout of the two different directory names).
- TUI session browser: `src/ui/components/SessionBrowser.mjs` — already exists; a CLI `sessions` namespace must call the *same* `session.mjs` functions, not reimplement listing.

### Init / project intelligence
- **Current `/init` is a stub** (`src/ui/commands.mjs:209-223`): creates `.upstage/{,checkpoints,agents,skills}` empty directories and returns `".upstage/ 디렉토리 초기화 완료"`. **No repository analysis, no file generation, no UPSTAGE.md.** No root `UPSTAGE.md` exists in this repo itself.
- Real intelligence infra already exists to build a genuine `/init` on: `repo_map` tool (`src/tools/builtin/repo-map.mjs`, walks the workspace via `collectWorkspaceFiles`, parses each file with `parseSourceFile` from the tree-sitter adapter, returns file→symbols); `find_symbol`/`find_references`/`list_modules`/`index_health` (`src/tools/builtin/intelligence-tools.mjs`); the incremental indexer (`src/indexer/intelligence.mjs`, `src/indexer/store.mjs`).
- `UPSTAGE.md` project-context-file convention (analogous to CLAUDE.md) is already documented in CLAUDE.md as "merged into the system prompt" — the loader for this exists somewhere in `src/agent/context-builder.mjs`'s neighborhood (not read in this pass; verify path at implementation time) — 3.2's real `/init` needs to *write* to the same file this loader already *reads*.

### Security / configuration
- **Settings cascade** (`src/config/settings.mjs`): `SETTINGS_SCHEMA` (single source of defaults — model, permissions, hooks, loopBudget, etc.), `deepMerge()`, `applyEnvOverrides()` (reads `UPSTAGE_*` env vars), `loadSettings({cwd})` merges `~/.upstage/settings.json` → `<cwd>/.upstage/settings.json` → `<cwd>/.upstage/settings.local.json` → env overrides → (CLI flags, applied by the caller in `src/cli/index.mjs`). **No per-key source tracking** — `loadSettings()` returns a flat merged object with no record of which layer set which value. This is the concrete gap behind §T's "effective config with source precedence" being real work, not just formatting.

- **Policy engine** (`src/core/policy/engine.mjs`): `PolicyEngine` with per-action-class rules (`read|write|exec|network|git|publish`, each `{allow, requiresConfirmation}`), workspace-boundary path checks (`isWithinTrustedRoot`), `SECURITY_OVERRIDE` env escape hatch, Korean PII scanning integration (`scanKoreanPII`/`summarizeFindings` from `src/permissions/korean-pii-check.mjs`). - **Permissions** (`src/permissions/`): `checker.mjs` (6 modes: `default|bypassPermissions|acceptEdits|auto|dontAsk|plan`), `path-check.mjs`, `injection-check.mjs`, `korean-pii-check.mjs`, `sandbox.mjs`.
- **Cost cap already enforced live**, not just tracked: `src/config/defaults.mjs`'s `DEFAULT_LOOP_BUDGET.maxCostUsd = 5.0`; `src/agent/loop.mjs:813-818` stops the loop when `tokenBudgeter.totalCost() > budget.maxCostUsd`. Directly reportable in `doctor`'s Security section.
- **Git detection**: `isGitRepo()` already exists in `src/core/worktree.mjs:17` — reusable for `doctor`'s Project section, no new implementation needed.
- **Prior internal research already exists and is directly relevant**: `docs/roadmap-tui-and-features.md` §E (written 2026-09-03, one day before this plan) already scoped ACP ("real, maturing standard... 25+ agents and 12+ editor hosts as of 2026... the existing `upstage-bridge` NDJSON protocol is a bespoke one-off nothing consumes yet"), the `/init` gap, and session-export-over-existing-events, reaching materially the same conclusions this plan reaches independently in §3/§7/§K/§L. This plan treats that doc as background/superseded-by-this-plan for those specific items, not a citation of borrowed authority — it's included here because a fresh implementer should know it exists and why this plan doesn't contradict it.
- **Bridge protocol** (`src/bridge/bridge-server.mjs`, `src/bridge/server.mjs`): NDJSON-over-stdio, `initialize/prompt/cancel/ping` → `ready/initialized/event/result`. **Confirmed zero real consumers** by this audit — `grep -rln "BridgeServer|bridge-server"` across `src/`/`tests/`/`scripts/` returns only its own implementation and its own test (`tests/m29-bridge.test.mjs`). No editor extension exists against it.

### myeolinmalchi/upstage-cli
Verified via raw GitHub file fetches (source-level ground truth, not summarized).

- **Not published to npm** (`registry.npmjs.org/upstage-cli` → 404) despite having publish tooling — install requires git clone + `npm link`. Single commit day (2026-03-03), 2 stars, no CI, `npm test` is a literal TODO in its own README. **This repo should not defer to its maturity or scale — it is a useful UX/API reference, not a production bar to match.**
- **Stack:** TypeScript + Commander `^13.1.0` (its one dependency), `tsc` build.
- **Commands (exact, from source):** `parse <file> [-f md|html|text] [-m standard|enhanced|auto] [--ocr auto|force] [--json]`, `ocr <file> [--json]`, `extract <file> -s <json|@file> [-n name] [--json]`, `schema <files...> [--json]` (hard 3-file cap, client-enforced), `classify <file> -c <csv-categories> [--json]`, `embed <text> [-t query|passage] [--json]`, `install --skills`, `config set-key|show|reset`.
- **API key:** `UPSTAGE_API_KEY` env first, else `~/.config/upstage-cli/config.json` (`{"apiKey":...}`, `mode 0o600`).
- **`install --skills` mechanism:** copies one static bundled file, `skills/upstage/SKILL.md` (frontmatter: `name: upstage`, `description`, **`allowed-tools: Bash(upstage *)`**), into `<cwd>/.claude/skills/upstage/SKILL.md`. No templating, no per-target generation — relies entirely on Claude Code (and, per its README, other tools) reading the same `.claude/skills/` convention. The `allowed-tools: Bash(upstage *)` scoping pattern is worth adopting verbatim in this repo's own installed skill (§7.I).
- **Output convention:** `--json` everywhere = raw API passthrough; without it, each command hand-extracts the "useful" field. **No quiet mode. No retries. No streaming.** Exit codes are binary/unstructured (`process.exit(1)` on any failure with the raw API error printed to stderr).
- **License:** MIT confirmed, `Copyright (c) 2026 upstage-cli contributors` (generic attribution, not an individual). If any of its code (not just its UX pattern) is ever copied verbatim rather than independently reimplemented, this repo's own `LICENSE`/`NOTICE` must carry that copyright line — **this plan does not propose copying its code**, only its command-contract *shape*, so no attribution obligation is triggered by anything in this plan; flag this explicitly if a future task deviates from that.
- **What NOT to copy:** its single-file-only commands (no batch, `schema` capped at exactly 3 with no override), its stale/likely-broken embedding model names (`embedding-query`/`embedding-passage`, matching neither Upstage naming generation and claiming 4096-dim in its own SKILL.md against a live 1024-dim API), its lack of retry/timeout handling, and its lack of a `groundedness` command despite `package.json`'s description claiming one exists (dead/aspirational text in its own repo — a caution about trusting its README over its source).
- **What's genuinely good and worth this repo adopting:** the `-s @schema.json` file-reference convention for large flag values, `--json`-everywhere as a hard rule, and the "shell command, not MCP round-trip, saves tokens for an agent caller" framing as the explicit design thesis for standalone commands (§7.I builds on this directly).

### Agent Skills
Canonical spec at `agentskills.io` (open standard, originally developed by Anthropic). A skill = a folder with `SKILL.md` (only `name`+`description` required in frontmatter) + optional `scripts/`/`references/`/`assets/`. Three-stage progressive disclosure: discovery (name+description only, ~100 tokens/skill) → activation (full body on task match) → execution (bundled files loaded on demand) — **this repo's `SkillsLoader` already implements exactly this shape** (§2), it just hasn't been positioned as *the* interop surface yet.

Confirmed adopters (from `agentskills.io`'s live client list, ~45 entries): Claude Code (`.claude/skills/` project, `~/.claude/skills/` user), **OpenCode** (explicitly documented as reading the *same* `.claude/skills/`/`~/.claude/skills/` paths — zero-adapter compatible), Gemini CLI, Cursor, GitHub Copilot + VS Code Copilot Chat, ChatGPT/Codex ("building on the open Agent Skills standard"), JetBrains Junie, Goose, Roo Code, Kiro, and dozens more. No harness under the exact name "Pi" is listed; the closest match is `badlogic/pi-mono`'s `pi` agent, which documents its own (likely-compatible, not independently verified) skills support.

**Verdict for §I:** because several major targets (OpenCode confirmed, likely others) read the *identical* `.claude/skills/` path Claude Code uses, a single canonical `SKILL.md` body needs **no per-target templating for the file format itself** — only the install *location* varies per target, and even that collapses to one location for several targets at once. This directly informs Task 7.9's design: copy/symlink one canonical skill body into whichever of `.claude/skills/`, a target's own documented skills path (if distinct), etc. are applicable, rather than generating N different bodies.

### ACP
Created by Zed Industries, released **August 2025**, JSON-RPC 2.0 over stdio (local; HTTP/WebSocket remote is documented but explicitly described as still under development). Current **stable protocol version: 1**, versioned independently of SDK/schema package releases (lower churn risk than a pre-1.0 protocol). Official SDKs: Rust, TypeScript, Python, Java, Kotlin.

**Purpose vs. MCP:** MCP = agent→tools; ACP = editor→agent. Complementary, commonly both spoken by one agent process — matches this repo's own `docs/roadmap-tui-and-features.md` framing exactly.

**Methods an agent (server) must implement:** `initialize` (protocol-version + capability negotiation), `session/new`, `session/load` (resume — replays history as `session/update` notifications, optional capability), `session/prompt` (the turn), `session/update` (agent→client streaming: message chunks, tool-call status, plan updates), `session/request_permission` (agent asks the client to authorize a sensitive op before running it — this is the piece that must map onto this repo's existing `PolicyEngine`/permission-mode decisions rather than duplicate them). Client-provided capabilities an agent may call: `fs/read_text_file`, `fs/write_text_file`, `terminal/create|output|wait_for_exit|kill|release`, `mcp/connect|disconnect|message`. Cancellation is a first-class message.

**Adoption:** Clients (hosts): Zed (originator), JetBrains IDEs, Neovim (two independent plugins — CodeCompanion, `avante.nvim`), Emacs, Obsidian; a joint Zed+JetBrains ACP Registry (launched Jan 2026) listed 40+ agents by April 2026, 50+ by late June 2026. Agents (servers): **Gemini CLI is the flagship/reference implementation** (Zed built its ACP support around it). This repo's own prior research (`docs/roadmap-tui-and-features.md`) additionally names Claude Code and opencode as ACP-capable agents, consistent with but not independently re-verified in this pass.

**Sizing vs. this repo's bridge:** the existing `BridgeServer` (`initialize/prompt/cancel/ping` → `ready/initialized/event/result`) is structurally close to ACP's `initialize`/`session/prompt`/cancellation/`session/update` shape, but is bespoke newline-JSON (not JSON-RPC 2.0) and has **no permission-request round-trip** — the one genuinely new piece of protocol work ACP requires beyond what the bridge already models. Given zero real bridge consumers exist today (§2), this is a real-but-bounded, not "small," lift: roughly 5 required methods, a JSON-RPC framing layer, and one new permission-mapping path. **This plan scopes ACP as P2/stretch** (§12), consistent with the prompt's explicit permission to do so when research shows it's larger than the rest of the release — it is not "small," but it is also not unbounded; a fresh implementer can reasonably estimate it at the same order of magnitude as the entire MCP client implementation this repo already shipped in 3.0/3.1.

### Comparable CLI patterns
- **`doctor`:** Salesforce CLI's plugin pattern is the clearest reference — each check emits `{testName, status}` with `status ∈ {pass,fail,warn,unknown}`, `--json` as a first-class output mode, explicitly designed to be safe to paste into a bug report (no secrets). This maps directly onto §7's `doctor` design (§7.10).
- **Installers:** rustup/Deno/Bun all follow `curl -fsSL <url> | sh` with platform/arch detection and a fixed install location; rustup additionally publishes SHA-256 checksums per release and hardens the `curl` invocation itself (`--proto '=https' --tlsv1.2 -sSf`) against protocol-downgrade tricks — a cheap addition this repo's installer lacks. A known real failure mode (truncated download still executing) is why atomic replace (download to temp → verify → move into place) is standard — this repo's installer currently does the *opposite* (`rm -rf` the install dir before extracting), a genuine robustness gap (§7.19).
- **`/init`-equivalent:** no new information beyond §2's own findings and the repo's prior research doc.

`src/upstage/client.mjs` wraps `fetchWithRetry` (`src/model/fetch-utils.mjs`) with the Upstage base URL/auth header, so every module below it inherits retry-on-429/5xx for free — something **none** of the three existing HTTP clients currently have. **Deliberate departures from the prompt's candidate shape:**

### Backwards compatibility
All existing flags/commands (`-p/--prompt`, `-m/--model`, `--session`, `--new-session`, `--reset-session`, `--confirm-patches`, `--bridge-json`, `--permission-mode`, `--system-prompt`, `--cwd`, `--add-dir`, `--max-turns`, `--max-time`, `--allowedTools`, `--disallowedTools`, `--lang`, `-v/--debug`) are untouched — the router only adds new top-level command names that don't collide with any existing flag or the existing `chat|ask|tui` set (verified: none of `doctor|init|version|update|uninstall|migrate|completion|models|context|config|auth|mcp|tools|skills|agents|plugins|sessions|parse|ocr|extract|schema|classify|embed|groundedness|acp` collides with `parseCliArgs`'s existing token set). The new `-e`/`--reasoning-effort` flag is additive (omitting it preserves today's default behavior).

### stdout/stderr conventions
- Human-readable result → **stdout**. Progress/diagnostic chatter (e.g. "Downloading...", retry notices) → **stderr**.
- `--json` on any command: stdout carries **only** the JSON result (single `JSON.stringify(...)`, no trailing human text mixed in), stderr may still carry progress notices unless `--quiet` is also passed.
- `--quiet`: suppress non-essential stderr chatter; the command's primary result (stdout) is unaffected. Not added to every command blindly — only ones with meaningful "chatter" to suppress (installer-style commands, `mcp test`, `update`); a single-shot command like `embed` has nothing to quiet.

### JSON conventions
- Every new standalone Upstage-utility command and every introspection command supports `--json`.
- JSON output is the **raw or lightly-normalized API/data result**, not a wrapper envelope with a `success` field — matches `myeolinmalchi/upstage-cli`'s convention (§3) and keeps output pipeline-friendly (`upstage classify f.pdf --categories a,b --json | jq .label`).
- Exception: commands that synthesize data not present in a single API call (`doctor --json`, `mcp list --json`) use a documented flat object shape (defined per-task in §12) since there's no "raw API response" to pass through.

### Exit codes
| Code | Meaning |
|---|---|
| 0 | Success |
| 1 | General/unexpected error |
| 2 | Usage error (bad flags/args — mirrors `myeolinmalchi/upstage-cli`'s pattern but adds this specific code so scripts can distinguish "you called it wrong" from "it ran and failed") |
| 3 | Upstream Upstage API error (4xx/5xx from the API itself, after retries exhausted) |
| 4 | Missing/invalid configuration (no `UPSTAGE_API_KEY`, unreadable settings file, etc.) |

Every new command must use this table consistently — §12's per-task acceptance criteria call out the exact code(s) each command must return.

## 7. Feature Designs

### 7.A — Shared Upstage API layer
See §5's diagram. Modules and their exact responsibility:
- `src/upstage/errors.mjs` — `class UpstageApiError extends Error { constructor(message, {status, code, retryable, body}) }`. Every module throws this, never a bare `Error`, so callers (CLI exit-code mapping, `doctor`, MCP tool `isError`) can branch on `.status`/`.retryable` without string-matching messages.
- `src/upstage/client.mjs` — `async function upstageRequest({path, method, body, apiKey, baseUrl, isMultipart, formFields, fileField, timeoutMs})` wrapping `fetchWithRetry` (reused, not reimplemented) + `UPSTAGE_API_KEY`/`UPSTAGE_API_BASE_URL` resolution (reusing the exact same env-var names `read-document.mjs`/`upstage-adapter.mjs` already use) + JSON/multipart body construction (the multipart-building logic in `read-document.mjs:31-48` moves here verbatim, since it's already correct and has no library dependency worth adding). Throws `UpstageApiError` on non-2xx.
- `src/upstage/documents.mjs` — `parseDocument({path, format, mode, ocr})`, `ocrDocument({path})`, both calling `POST /v1/document-digitization` per §3's confirmed shape (sync only for 3.2 — async job polling is explicitly out of scope, see §14 rationale... *actually keep in scope, see Task 7.2 acceptance* — sync-first, async as a stretch within the same task).
- `src/upstage/extraction.mjs` — `extractStructured({path, schema})`, `generateSchema({paths})` (paths: max 3, enforced client-side per confirmed API constraint).
- `src/upstage/classification.mjs` — `classifyDocument({path, categories})`.
- `src/upstage/embeddings.mjs` — `embed({texts, type})` (`type: "query"|"passage"`), using the **corrected** current model names `solar-embedding-2-query`/`solar-embedding-2-passage` (§3) — this single change, applied once here, fixes both existing embedding clients' staleness when they're refactored to call through it.
- `src/upstage/groundedness.mjs` — `checkGroundedness({context, answer})`, using model id `groundedness-check` **pending the live-verification step in Task 7.7** (do not ship the corrected default without confirming the response label enum live, per §3's "uncertain" flag).
- **Refactor, not rewrite, the three existing callers**: `read-document.mjs`, `semantic-search.mjs`, `check-groundedness.mjs`, and `retriever/providers/upstage.mjs` all become thin callers into `src/upstage/*.mjs`, deleting their private HTTP code. This is where the "three duplicated clients" finding in §2/§4 actually gets fixed — not a side-effect of adding new commands, but the direct payoff of doing them through a shared layer.

### 7.B–7.H — parse / OCR / extract / schema / classify / embed / groundedness (standalone commands)
Each is a thin `src/cli/commands/<name>.mjs` calling the matching `src/upstage/*.mjs` function, formatting per §6's conventions. Agent-tool exposure: `read_document`/`semantic_search`/`check_groundedness` already exist and get refactored (7.A) rather than duplicated; **extraction/schema-generation/classification get no new agent tool in 3.2** — CLAUDE.md principle 9 ("do not add built-in tool #31 just because it is easy") applies directly here, and nothing in the original feature request requires it; an agent that needs structured extraction can already shell out to `upstage extract` via `run_shell`, which is in fact the more token-efficient path per §3's cross-source-confirmed design thesis. Flag/output details, file-type validation, and `@file` schema loading are specified per-task in §12 (Tasks 7.1–7.7).

### 7.I — Agent Skills export/install
`upstage skills install [--target <name>]` copies **one canonical skill body** (a new first-party skill directory, e.g. `skills/upstage-utilities/SKILL.md`, following this repo's own existing skill format exactly — see `skills/document-ai-parsing/` for the pattern to match) into `.claude/skills/upstage-utilities/` (and, if `--target` names another detected agent path, that path too). Per §3's finding that several major targets read the identical `.claude/skills/` directory, **no per-target templating of the body is needed for 3.2** — only the destination path list varies, and the default (no `--target`) installs to every detected target path that exists on the host (i.e., a directory that plausibly belongs to a known agent, checked by presence, not by guessing which agents are "installed"). Frontmatter includes `allowed-tools: Bash(upstage *)` (adopting `myeolinmalchi/upstage-cli`'s scoping pattern, §3) so a permission-aware host agent can grant exactly the shell surface this skill needs. Skill body content: teaches the reader to prefer `upstage parse/extract/classify/embed/groundedness` shell invocations over asking the host agent to reimplement Upstage calls itself, and documents each command's flags.

### 7.J — Real `/init`
Replace `src/ui/commands.mjs`'s `/init` handler entirely. New flow: run `repo_map`/`find_symbol`/`list_modules` (existing tools, invoked directly as functions — not through the agent-tool-call loop, since `/init` is deterministic and shouldn't burn an LLM turn just to gather facts) to build Architecture/Entry-Points/Important-Directories sections; detect build/test/lint/typecheck commands from `package.json` `scripts` (already how this repo's own `npm run check/lint/test` are defined — reuse the same detection heuristic already implicit in `run-linter.mjs`/`run-tests.mjs`/`run-typecheck.mjs`'s own command-detection, factored out if not already a standalone function). Output target: `UPSTAGE.md` (project root), written inside a generated-block marker:
```
<!-- upstage:generated:start -->
...generated content...
<!-- upstage:generated:end -->
```
On re-run: if `UPSTAGE.md` exists, replace only the content between the markers, leaving anything the user wrote outside them untouched; if no markers exist yet in an existing hand-written file, **append** a new generated block rather than overwriting the file. `/init --refresh` forces regeneration even if a generated block already looks current (no staleness heuristic needed — regeneration is cheap and deterministic). `/init --dry-run` prints the would-be content to stdout/chat without writing. CLI-level equivalent: `upstage init [--refresh] [--dry-run]` calling the identical underlying function so the TUI slash command and the CLI command are one implementation, not two.

### 7.K — ACP (P2/stretch)
Scoped per §3: a new `src/acp/server.mjs` speaking JSON-RPC 2.0 over stdio, implementing `initialize`, `session/new`, `session/prompt` (bridging into the existing `runAgentLoop` async generator exactly as `src/bridge/bridge-server.mjs` already does — the event-translation logic is the reusable part), `session/update` (translating `AgentEvent`s into ACP's streaming-update shape), and `session/request_permission` (bridging into the existing `PolicyEngine`/`createInteractiveApprovalHandler`/`createPermissionChecker` machinery rather than building a second permission model). `fs/*`/`terminal/*` client-provided capabilities are **not** consumed in 3.2 — the agent keeps using its own tools (`read_file`/`run_shell`) rather than delegating file/terminal access to the ACP client, since this repo's own tool/policy/sandbox stack is more mature than what a generic ACP client would provide. Entry point: `upstage acp`. Given §3's sizing note (comparable in scope to the existing MCP client work), **this task ships only if P0/P1 work lands with schedule headroom** — see §12's explicit P2 gating.

### 7.L — Session export
`upstage sessions export <id> --format md|json|jsonl` reads the existing session JSON (`loadSession(id)`, already sanitized per §2) and formats it three ways: `json` = the sanitized session object as-is; `jsonl` = one line per `runtimeEvents`/`history` entry (for streaming/log-processing tooling); `md` = a human-readable transcript (prompts, responses, tool calls with truncated args/results, patches applied, verification results, token usage/cost — all already present in the sanitized session shape per §2's audit of `session.mjs`'s `sanitizeValue`). **Redaction default:** tool call *arguments* and *results* are already truncated at 500 chars/20 array items by the existing sanitizer — 3.2 adds one more default: raw file contents inside `write_file`/`edit_file` tool results are elided to a diff-stat-only summary unless `--include-tool-io` is passed, since a full file body is the single most likely place a secret or large chunk of proprietary source ends up in an exported artifact meant to be pasted into a bug report or shared with a teammate.

### 7.10 — `doctor`
`upstage doctor [--json]` runs a fixed list of checks (Core/Upstage/Project/Extensions/Security/Verification per the prompt's own outline), each producing `{name, status: "pass"|"fail"|"warn", detail}` (Salesforce-CLI-pattern, §3). Implementation reuses, does not reimplement: `checkProviderKeys()` (Upstage section), `isGitRepo()` + settings-cascade read (Project section), `loadMcpServerConfigs`+`connectConfiguredServers` with a short timeout (Extensions/MCP), `ToolRegistry.list()` grouped by `source` (Extensions/tools), `SkillsLoader`/`AgentLoader`/`PluginLoader` (`.load()` + `.list()`/`.skills.size` etc.) (Extensions), `DEFAULT_LOOP_BUDGET.maxCostUsd`/permission mode/sandbox flag from settings (Security), and a lightweight "does `npm test`/`npm run lint`/`npm run check` exist in `package.json` scripts" check reusing whatever detection `/init` (7.J) builds (Verification) — **the two tasks should share one command-detection helper**, not duplicate it. **Never** prints `UPSTAGE_API_KEY`'s value, MCP server `env`/`headers`, or any other secret — only presence/absence and, where meaningful, a redacted shape (`"configured (starts with up_...)"` at most).

### 7.Q — MCP introspection
`upstage mcp list [--json]` calls `loadMcpServerConfigs()` + `connectConfiguredServers()` (short timeout, e.g. 3s) and prints a table (`NAME TRANSPORT STATUS TOOLS`, matching the prompt's example exactly) — a server that fails to connect shows `STATUS=failed`, `TOOLS=-`, and **does not abort the listing** (this is already `connectConfiguredServers`'s existing isolation behavior, §2 — the command just needs to render it). `mcp status` = a narrower single-line-per-server summary. `mcp test [<name>]` re-runs the connect attempt for one (or all) servers and reports pass/fail with the actual error message. `mcp tools <name>` connects and calls `tools/list` on that one server, printing tool names/descriptions/count. `mcp show <name>` prints the server's config with `env`/`headers` values **redacted to key-presence only** (`OPENAI_API_KEY: "***"` never the value) — this is the one place in this feature where a naive implementation would leak secrets, so the redaction step is a named acceptance criterion in Task 12's corresponding entry, not an afterthought.

### 7.R — tools/skills/agents/plugins introspection
`upstage tools list [--json]` = `ToolRegistry.list()` grouped/sorted by `source` (`BUILTIN|MCP|PLUGIN|DISCOVERED`, per the prompt's exact taxonomy — note `ToolRegistry` currently tags MCP tools `"mcp"` and discovered tools `"discovered"` lowercase; the CLI display layer uppercases for the table, it does not change the underlying tag). `tools show <name>` prints one tool's full schema/description/source. `skills list`/`show`, `agents list`/`show`, `plugins list`/`show` are the equivalent thin wrappers over `SkillsLoader.list()`/`.get()`, `AgentLoader`'s existing list/get (verify exact method names at implementation time — not confirmed in this pass), `PluginLoader`'s loaded-plugin list. **No CRUD** — visibility only, per the prompt's explicit instruction.

### 7.S — Sessions CLI
`upstage sessions list [--json]` = `listSessions()` (already exists) formatted as a table (id, updatedAt, cwd, message count). `sessions show <id>` = `loadSession(id)` pretty-printed (human) or raw (`--json`). `sessions resume <id>` = the exact same code path `--session <id>` already triggers in `main()` (`src/cli/index.mjs`) — this command is a documented alias/entry point into existing resume logic, not new resume logic. `sessions export <id>` = §7.L. Deletion is **not** included in 3.2 (the prompt makes it optional and gates it on "existing semantics make it safe" — `resetSession()` exists but resets-and-creates-new rather than deletes-and-confirms-gone, which isn't quite the right primitive for a user-facing `sessions delete`; revisit in a later release rather than force a mismatch now).

### 7.T — Config introspection
`upstage config list [--effective]` is the one place genuinely new logic is needed (§4): `loadSettings()` must optionally track, per top-level key, which cascade layer last set it (global settings / project settings / project local / env override / CLI flag). Implementation approach: run the existing merge four times with progressively more layers (schema-only, +global, +project, +local, +env), diffing each pass against the previous to attribute the *last* layer that changed each key — this reuses `deepMerge`/`applyEnvOverrides` exactly as they exist today rather than rewriting the cascade, at the cost of running it multiple times (cheap — it's a handful of small JSON files). `config get <key>`/`config set <key> <value>` operate on `<cwd>/.upstage/settings.json` specifically (never silently writing to the global or local-override file) using dot-path key access. `config path` prints the resolved file path for the active project. `config edit` opens `$EDITOR` on that same file (reusing the `EDITOR` env var already in `ENV_SCHEMA`).

### 7.U — Auth introspection
`upstage auth status` prints, per provider, `Source` (which env var is set — reusing `checkProviderKeys()`), `Key` (`configured`/`not configured`, never the value), and, for the active provider only, `API: reachable/unreachable` (one lightweight live call — e.g. a minimal chat-completions request with `max_tokens: 1` or a HEAD-equivalent, decided at implementation time to minimize cost). `auth test` forces that live check for a named provider regardless of which is "active." No `login`/`logout` — this repo's credential handling is env-var/settings-file based with no session-token concept, so per the prompt's explicit guidance, credential UX beyond status/test is out of scope.

### 7.V — Version/update
`upstage version [--verbose]` and `upstage --version` print `upstage-cli <version>` (from `package.json`) by default; `--verbose` adds commit hash (`git rev-parse HEAD` if `isGitRepo()`), build date, install type (see below), runtime (`Bun.version`/`process.version`), platform (`process.platform`/`process.arch`). **Install-type detection** (shared with `doctor` and dev-link, §7.N): a compiled standalone binary is detected via `process.execPath` pointing outside any `node_modules`; an npm/global install via `process.execPath`'s path containing the package's `node_modules/.bin` or a global npm prefix; a dev-link via a marker file written by `scripts/dev-link.sh` itself (simplest reliable signal — see 7.N). `upstage update --check` reports whether a newer GitHub release exists (compares `package.json` version to the latest release tag, one network call) without installing anything. `upstage update` behavior branches on install type: standalone binary → download+checksum-verify+atomically-replace the current binary (reusing the installer's own verification logic, not a separate implementation); dev link → print "this is a development checkout — `git pull` it yourself" and exit 0 without touching anything; npm install → print "installed via npm as `@jackochesstern/upstage-cli` — run `npm install -g @jackochesstern/upstage-cli@latest`" and exit 0 without invoking npm on the user's behalf (per the prompt's explicit instruction not to secretly invoke package-manager operations).

### 7.N — Development-link workflow
`scripts/dev-link.sh`: writes a small wrapper script to `~/.local/bin/upstage` (or `$UPSTAGE_BIN_DIR`) that `exec`s `bun <resolved-repo-root>/src/cli/index.mjs "$@"` — critically, the wrapper resolves the repo root at *link time* (baked into the script, an absolute path) so the resulting `upstage` command works from any cwd, and passes `"$@"` through unchanged so the target project's cwd is whatever the user was in when they ran `upstage`, not the repo's cwd (i.e. the wrapper must **not** `cd` into the repo — `bun <abs-path>/src/cli/index.mjs` does not require the shell's cwd to change, Node/Bun resolve relative imports from the script's own path). Writes a marker (`~/.upstage-cli/dev-link.json` or similar, `{repoRoot, linkedAt}`) that `doctor`/`version --verbose` read to report "development build" and the repo path. Before overwriting an existing `~/.local/bin/upstage`, checks whether it's already a dev-link wrapper (via the marker or a recognizable comment in the script) — if it points at a *different* repo, warns and requires `--force`; if it looks like a real production install (e.g. a symlink into `~/.local/share/upstage-cli/`, matching `scripts/install.sh`'s own layout), refuses without `--force` and explains why. `scripts/dev-unlink.sh` removes the wrapper and marker, restoring nothing (the user re-runs the production installer if they want it back — this script does not attempt to "remember" a prior production install to restore, that's needless complexity for a dev tool). **Windows story:** a `scripts/dev-link.ps1` writing a `.cmd`/`.ps1` shim onto `%USERPROFILE%\.local\bin` or similar, added to `PATH` if missing (with an explicit printed instruction rather than silently editing the user's registry/profile) — Bun's Windows support is real (`bun.sh` ships Windows builds) so this is not a "WSL required" situation, just a different shim mechanism.

### 7.19 — Installer hardening
`scripts/install.sh` changes: (1) accept `UPSTAGE_VERSION` env var, defaulting to `latest` — download `releases/download/${UPSTAGE_VERSION}/...` instead of always `releases/latest/download/...`; (2) download the release's published `.sha256`/checksum file alongside the archive and verify before extracting (fail loudly, do not install, if verification fails — the release workflow, §12's corresponding task, must start publishing checksums for this to be possible, since none exist today); (3) extract into a fresh temp directory, verify the extracted binary runs (`--version` smoke test) *before* touching `$INSTALL_DIR`, then atomically swap (`mv` the old dir aside, `mv` the new dir into place, remove the old one only after the swap succeeds — not `rm -rf` up front); (4) if `$INSTALL_DIR` already exists and looks like a *different* kind of install (e.g. a dev-link marker present, or a version newer than what's being installed without an explicit `UPSTAGE_VERSION` override), print a warning and require confirmation or `--force` rather than silently overwriting; (5) print PATH diagnosis using an actual `command -v upstage` check (not just a string-match against `$PATH`) so it correctly reports success/failure even in shells with unusual PATH setups. Windows: this script still explicitly declines and points at the release zip (unchanged) — a native Windows installer is out of scope for 3.2 per the prompt's "reasonable Windows development story" bar being about dev-link (7.N), not the production installer; `upstage doctor` and the release zip's own README remain the Windows install path.

### 7.15 — `upstage context` (repo-level context budget) + TUI `/context`
Two related surfaces answering "where did my context budget go," one pre-session (deterministic, no model call) and one live-session — research confirmed **no competitor (Claude Code/Gemini CLI/Codex CLI/OpenCode) has the pre-session one**, every `/context`-equivalent found is live-session-only, so this half is a genuine differentiator, not a catch-up feature:
- `upstage context [--json]` (standalone CLI, new): without starting a session, reports (a) `UPSTAGE.md`/project-instructions token cost (tokenizing the same merged content `context-builder.mjs` injects), (b) repo-map token cost at current settings (`buildIntelligenceIndex`/`rankRepoMap`'s output, tokenized), (c) an estimated fixed system-prompt/tool-schema baseline, and (d) the resolved model's context limit (`model-capabilities.mjs`), shown as a percentage of budget.
- TUI `/context` (replaces the current thin `/memory` stub, `src/ui/commands.mjs:255-263`): live-session breakdown matching the confirmed Claude Code category list — system prompt / builtin tools / MCP tools / project instructions / skills / conversation history / free space — computed via the same `_contextManager` already powering `/compact` and `/cost` (both already exist and work; `/context` is the missing detailed breakdown between them, not new plumbing).
Both share one token-counting function; `context-builder.mjs` and `model-capabilities.mjs` are the only pre-existing dependencies.

### 7.16 — `upstage models list/info`
`upstage models list [--json]` prints every entry in `model-capabilities.mjs`'s table (id, context limit, reasoning/parallel-tool-call/response-format support, current default marker) plus other configured providers' known models where `getProvider()` exposes them; `upstage models info <model> [--json]` prints one model's full capability row. Pure read of an existing in-memory table — no network call, no new data source. Research confirmed no mainstream competitor has a *standalone command* for this (Claude Code/Codex CLI expose it only via an interactive `/model` picker, and a GitHub Copilot CLI user complaint — issue #2474 — explicitly asks for exactly this kind of inline capability info) — another differentiator, not parity work. TUI `/model` (currently a one-line stub, `src/ui/commands.mjs:122-127`) is upgraded to call this same function rather than duplicating it (principle 2).

### 7.17 — Reasoning-effort control (`-e`/`--reasoning-effort`, `/effort`)
Per the original plan's §13 risk note (Upstage's live `reasoning_effort` enum — `none|minimal|low|medium|high|xhigh|max` — is richer than this repo's current `VALID_REASONING_EFFORTS = {low,high}`, `upstage-adapter.mjs:32`) and confirmed by this round's research (Claude Code and Codex CLI both let effort change **mid-session without a restart** — Codex CLI via `/effort high` or `-e`/`--reasoning-effort`; Gemini CLI notably does **not** have this yet, per multiple of its own open feature requests citing Claude Code as the bar): (1) widen the validated enum to match the live API once Task 7.1's live-verification confirms it, (2) add a `-e`/`--reasoning-effort <level>` CLI flag (mirroring Codex CLI's exact flag shape) applied to both `ask` and interactive sessions, (3) add a TUI `/effort <level>` slash command for mid-session changes, reusing the instance-level `reasoningEffort`/`setReasoningEffort()` mechanism the §2 audit already found partially implemented on `UpstageAdapter`. No new config layer.

### 7.18 — `upstage completion`
`upstage completion bash|zsh|fish|powershell` generates each shell's completion script **at runtime from `src/cli/router.mjs`'s command table** (Task 12.1) and writes it to stdout — the confirmed `gh`/Cobra pattern (generation, not static template files), which works unmodified inside a `bun build --compile` standalone binary with no bundling concerns (unlike skill files, which needed a special-cased path per §2). PowerShell must be written and tested against `Register-ArgumentCompleter -Native` from the start — confirmed real gotcha, omitting `-Native` and adding it later does not behave the same. Output is printed for the user to redirect/eval themselves (`gh completion -s bash | ...` is the exact model) — this project must not write to a user's `.bashrc`/`.zshrc`/profile automatically.

### 7.20 — `upstage uninstall [--purge]`
Scope discipline is the key design decision, per research contrasting rustup's `self uninstall` (removes only what rustup itself manages, correctly leaves sibling package-manager installs alone) against Deno's `deno uninstall` (a confusingly-named command that doesn't actually remove Deno itself). Default `upstage uninstall` removes only the binary, its `$BIN_DIR` shim/symlink, and the dev-link marker if present; it does **not** touch `~/.upstage/` (settings) or `~/.upstage-cli/sessions/` (session data) without an explicit `--purge`. Interactive confirmation by default; `-y`/`--yes` for scripted/CI use (mirrors `rustup self uninstall -y`). Reuses 7.N/12.9's install-type detection first, so the message is accurate per install type ("removing standalone binary at X" vs. "this is an npm install — run `npm uninstall -g @jackochesstern/upstage-cli`" vs. "this is a dev-link — run `dev-unlink.sh` instead").

### 7.21 — `upstage mcp add/remove` (P2, safe surgical merge)
Included per explicit request; scoped carefully given a **concrete, currently-open risk found in research**: Claude Code's own `claude mcp add`/`add-json` has been observed to overwrite the entire `.mcp.json` instead of merging (GitHub issue #13281 — every other server entry lost), and `claude mcp remove` has been observed to expand `${VAR}` placeholders into literal secret values for *other, untouched* server entries during a full deserialize→reserialize write-back (GitHub issue #57131, titled "claude mcp remove reformats .mcp.json to reveal secrets"). **Do not implement the naive way** (`JSON.parse` → mutate → `JSON.stringify` the whole file). Implement a targeted text-level edit that only replaces the span of the one `mcpServers.<name>` key being added/removed, leaving every other key's original formatting/whitespace/placeholder text byte-for-byte untouched, written via temp-file + atomic rename (never in-place truncate). `--scope project` writes `.mcp.json` (the shared/interop file — the risky one); `--scope user` writes a separate user-level file, never `.mcp.json` — mirrors Claude Code's confirmed three-scope model (`local` default/unwritten, `project`, `user`). Given the implementation is strictly harder than it looks and the most prominent prior art is currently getting it wrong in production, this stays P2/stretch — read-only introspection (§7.Q, P1) ships regardless.

### 7.22 — `upstage plugins install <source>` (P2, minimal marketplace)
Research compared Claude Code's full plugin-marketplace format (`marketplace.json`, 7 distinct source types, a version-cached install directory, `strict` mode — a meaningfully large surface) against Gemini CLI's much smaller model (`gemini extensions install <github-repo-or-local-path>`, no registry/index concept, an explicit manual `update` step, no silent auto-tracking of upstream). **This plan deliberately adopts the Gemini-CLI-sized model, not Claude Code's**: `upstage plugins install <git-url|local-path>` clones/copies into `~/.upstage/plugins/<name>/` (reusing `PluginLoader`'s existing search dirs, §2) at install time, with no auto-update — `upstage plugins update [<name>|--all]` is a separate, explicit re-pull. No marketplace registry/index is built in 3.2. This is genuinely new scope (pulling third-party plugins *in*, distinct from 7.9's "push our own skill *out*") — correctly P2.

### 7.23 — `upstage migrate` (P2)
Moves between install methods (e.g. npm-global → standalone binary), reusing 7.N/12.9's install-type detection. Research on Claude Code's equivalent (`claude migrate-installer`/`claude install`) found a **confirmed production failure mode to avoid**: it leaves the old install method in place silently, and users hit PATH-shadowing bugs where the old npm shim keeps winning over the new native binary with no automatic fix-up (GitHub issue #28625 additionally documents `claude update` *misdetecting* a native install as npm-global and "fixing" it destructively). `upstage migrate --to standalone|npm` must prompt (or take `--remove-old`) to remove the previous install method rather than leaving a shadow copy — reusing 7.20's uninstall logic for "old npm install" (print the `npm uninstall -g ...` command) and "old dev-link" (run `dev-unlink.sh` automatically, since that one is fully within this project's control). Install-type detection must check the unambiguous dev-link marker before any path-shape heuristic (same principle as Task 12.9's failure modes) — Claude Code got exactly this wrong in production, so this is not a hypothetical caution.

### 7.24 — Small comfort additions
Three narrowly-scoped items, chosen because each closes a specific, cheap, well-precedented gap rather than chasing an open-ended feature list:
- **`.upstageignore`** (gitignore-syntax, hierarchical): excludes matched paths from **automatic context loading only** (repo map, project-instruction injection, intelligence index) — never from explicit tool-based access (`read_file`/`grep`, which stay governed by the existing permission/policy engine). Research flags that Claude Code's `.claudeignore` equivalent has had real leak incidents where files still appeared in context despite ignore rules — this task's acceptance criteria must include a test that an ignored file's content genuinely never appears in `context-builder.mjs`'s output, not just that the feature "exists."
- **`/bug`** TUI slash command: captures the last N turns plus `doctor`-equivalent environment info into a local file and prints the GitHub issue URL to paste it into — no automatic network submission, since this project has no telemetry-upload infrastructure to build on and inventing one is explicitly out of scope (§14).
- **`/model`/`/doctor` TUI-command consolidation**: `/doctor` (`src/ui/commands.mjs:178-195`) currently reimplements a small, separate diagnostic check from scratch — it should call the same check functions Task 12.3's `upstage doctor` uses (principle 2, "one implementation, multiple surfaces"), not maintain a thinner second copy; `/model` should call Task 7.16's `models info` function instead of its current one-line stub.

## 8. Security Review

### Secrets
No new command prints an API key, MCP `env`/`headers` value, or settings field flagged sensitive. `doctor`, `mcp show`, `config list`, `auth status`, and `sessions export` are the five surfaces that touch config/credentials — each has an explicit redaction rule in §7 above, and each gets a dedicated "no secret leakage" test in §10/§12 (not just a code-review assumption). `mcp add`/`mcp remove` (§7.21, P2) add a sixth surface with a *specifically confirmed* failure mode (secret-value expansion during a naive whole-file rewrite, per the Claude Code issue cited in §7.21) — its acceptance criteria require a test that other servers' `env`/`headers` placeholder text is byte-for-byte unchanged after an add/remove, not just "still valid JSON."

### PII
`sessions export` reuses the existing Korean-PII-aware sanitization path already present in `session.mjs`'s event storage (§2) — export does not need a *new* PII scan, since the data it reads was already sanitized on write. New standalone commands that send file content to Upstage (`parse`/`ocr`/`extract`/`classify`) do **not** run this repo's `korean-pii-check.mjs` before upload, because that check exists to gate the *agent's* autonomous actions, not a user's own explicit, interactive `upstage parse myfile.pdf` invocation — the user already chose to send that specific file. This is a deliberate scope boundary, stated explicitly here so it isn't mistaken for an oversight.

### Network operations
Every new Upstage-calling command declares `actionClass: "network"` wherever it goes through the tool/policy layer (agent-tool refactors in 7.A); standalone CLI commands are **not** gated by `PolicyEngine` at all (they're direct user invocations outside the agent loop, same trust boundary as the user running `curl` themselves) — this matches how `myeolinmalchi/upstage-cli` and every other CLI reference in §3 treats standalone commands, and is consistent with CLAUDE.md principle 3 ("deterministic utilities should not require an agent loop").

### MCP sanitization
`mcp show`/`mcp list` never serialize `env`/`headers` values (§7.Q) — enforced by a dedicated test that constructs a config with a fake secret value and asserts it never appears in either human or `--json` output.

### Exported sessions
Default redaction (raw file bodies elided unless `--include-tool-io`) is stated in §7.L; a test constructs a session containing a `write_file` result with recognizable "secret-looking" content and asserts the default `md`/`json`/`jsonl` export doesn't contain it.

### Installer/update integrity
Checksum verification (7.19) and atomic replace are the two concrete integrity properties this release adds; `upstage update`'s self-update path reuses the same verification code as the installer rather than a second implementation (§7.V). `upstage uninstall`'s scope discipline (§7.20 — only remove what this project's own installer/dev-link put in place, `--purge` required to touch settings/sessions) and `upstage migrate`'s explicit old-install-removal step (§7.23 — chosen specifically to avoid the PATH-shadowing bug found in Claude Code's production issue tracker) are this addendum's equivalent integrity properties.

### Third-party plugin/skill installation trust boundary
`upstage plugins install <git-url|path>` (§7.22, P2) clones/copies arbitrary third-party code onto disk and, once loaded by `PluginLoader`, that code can contribute hooks/MCP servers/agents that run with this project's normal permission/policy engine applied — same trust model as a user manually placing a plugin directory under `~/.claude/plugins` today, not a new privilege boundary, but worth stating explicitly: this command does not sandbox or vet the source, and its help text should say so.

## 10. Testing Strategy

### Unit
Every new `src/upstage/*.mjs` module gets a `tests/m33-upstage-<module>.test.mjs`-style file (continuing this repo's `m<N>-*` numbering — next free number is `m33` per §2's audit of existing test files, highest currently `m32`) using Node's built-in test runner, mocking `fetch`/`fetchWithRetry` at the module boundary (inject `{apiKey, baseUrl}` pointing at a local test HTTP server or a stubbed fetch) — **this closes the "zero tests" gap on `read_document`/`semantic_search`/`check_groundedness` identified in §2/§4** as a side effect of the refactor, since the shared layer is finally testable without live network calls in a way the raw-`node:https` originals weren't.

### CLI golden tests
Each new `src/cli/commands/*.mjs` gets a test invoking its handler function directly (not spawning a subprocess) with a fake `src/upstage/*.mjs` module (dependency-injected or mocked via Node's test-runner mocking) asserting: correct stdout for `--json` vs. human mode, correct exit code per §6's table for a simulated API error, and — for the introspection commands — correct behavior when the underlying subsystem returns partial/failed state (e.g. `mcp list` with one server failing to connect must still print the others, per §7.Q's explicit acceptance criterion).

### Integration
A small number of tests exercise the router (`src/cli/router.mjs`) end-to-end via `node --test` spawning the actual CLI entry point as a subprocess for a handful of representative commands (`upstage version`, `upstage doctor --json`, `upstage tools list --json`) to catch wiring mistakes the unit tests can't (argv parsing, module resolution, actual process exit codes) — kept small in number since subprocess tests are slow; most coverage stays at the unit/golden level above.

### TUI regression
No TUI *rendering* code changes in this plan (§2 confirms the TUI path is already correct) — the only TUI-adjacent change is `/init`'s handler (7.J) and `runInteractive`'s help text, covered by existing `tests/opentui/` conventions if `/init`'s slash-command handler has a dedicated test file already (verify at implementation time; add one if not).

### Release binary
`scripts/package-binary.mjs`'s existing smoke path (if any — verify) plus a new explicit check: after `bun build --compile`, run the produced binary with `--version` and `doctor --json` and assert both exit 0, catching the "works under `bun run` but not compiled" class of bug (e.g. a new command accidentally relying on `import.meta.url`-relative file reads the way `SkillsLoader` had to special-case, §2).

### Installer
A test harness (shell script or Node test invoking `scripts/install.sh` against a local fake "GitHub release" HTTP server serving a fixture archive + checksum) verifies: successful install, checksum-mismatch rejection, `UPSTAGE_VERSION` override actually changes the downloaded asset URL, and that a pre-existing dev-link install is detected and refused without `--force`.

### Windows
Given the primary dev/CI environment for this session is Windows (per the environment block), and per-principle-13 ("Linux/macOS/Windows behavior must be considered explicitly"): `scripts/dev-link.ps1` gets a manual verification checklist in its own task (§12) since full Windows CI coverage is a larger investment than this release's scope — at minimum, `npm run check`/`npm test` must keep passing on Windows (already true today, per this session's own PowerShell-primary environment) and the new CLI commands must not use any POSIX-only shell assumptions (already true — they're `.mjs`, not shell scripts, except the two installer/dev-link scripts which are explicitly platform-forked).

### MCP
Reuses the existing `tests/m17-mcp-server.test.mjs`/`m18-mcp-client.test.mjs`/`m19-mcp-http.test.mjs` patterns for any new MCP-server `TOOLS` entries (7.A's MCP exposure) and adds `tests/m33-mcp-introspection.test.mjs`-equivalent coverage for the new `mcp list/status/test/show` commands specifically (not already covered by the existing client/server tests, which test the protocol layer, not the CLI layer).

### Upstage live tests vs. offline mocks
All tests in this plan run offline against mocked/injected HTTP responses by default (consistent with this repo's existing test discipline — no test in the current suite appears to make a live Upstage call). A small, explicitly-separate, opt-in live-verification pass (documented in a task's "Implementation" notes, not part of `npm test`/CI) is required specifically for the two "uncertain" findings in §3 (schema-generation endpoint path discrepancy; groundedness response label enum) before those two defaults ship — gated behind `UPSTAGE_API_KEY` being present and a manual invocation, never part of automated CI, per this repo's own "mock planner runs without a key" convention (CLAUDE.md).

Dependencies: Task 7.1's live-verification of Upstage's actual `reasoning_effort` enum (do not widen `VALID_REASONING_EFFORTS` past what's live-confirmed).
Files: MODIFY `src/model/upstage-adapter.mjs` (widen `VALID_REASONING_EFFORTS`); MODIFY `src/config/cli-args.mjs` (add `-e`/`--reasoning-effort <level>`); NEW handler in `src/ui/commands.mjs` for `/effort <level>`.
Tests: `tests/m30-model-capabilities.test.mjs` (extend existing file, don't create a parallel one) — asserts the widened enum is validated correctly and an invalid level is rejected with a clear error before any network call.
Acceptance: `upstage ask "..." -e high` sends the correct `reasoning_effort` value; `/effort medium` mid-session changes it without restarting (verified by asserting the next request uses the new value, not by restarting anything).
Failure modes: a model that doesn't support a given effort level (per `model-capabilities.mjs`'s `supportsReasoningEffort` flag, and Upstage's own confirmed "solar-mini rejects `reasoning_effort` with HTTP 400" behavior) must fail with a clear client-side message, not surface a raw 400 from the API.

**Task 7.18 — `upstage completion`**
*P1.* Dependencies: 12.1 (router) — the command table this generates from must exist first.
Files: NEW `src/cli/commands/completion.mjs`.
Contract: `generateCompletion(shell, commandTable)` → shell-script text, one function per shell (`bash|zsh|fish|powershell`), reading the router's command tree directly (no separate hardcoded command list to keep in sync).
Tests: `tests/m33-completion.test.mjs` — asserts every top-level command name from §6's tree appears in each shell's generated output.
Acceptance: `upstage completion bash | bash -n` (syntax-check only, no execution) passes for the bash output; PowerShell output uses `Register-ArgumentCompleter -Native` (verified by grep in the test, not by running PowerShell in CI given the primarily-Windows-dev-but-cross-platform-target nature of this repo — note the actual interactive behavior needs a manual check on Windows per §10).
Failure modes: regenerating the completion table by hand instead of walking the live router object would silently drift out of sync the first time a command is added — the implementation must introspect `router.mjs`'s table, not duplicate it.

**Task 7.20 — `upstage uninstall [--purge]`**
*P1.* Dependencies: 12.1 (router); install-type detection shared with 7.N/12.9.
Files: NEW `src/cli/commands/uninstall.mjs`.
Contract: default removes binary + `$BIN_DIR` shim/symlink + dev-link marker only; `--purge` additionally removes `~/.upstage/` and `~/.upstage-cli/sessions/`; `-y`/`--yes` skips the interactive confirmation.
Tests: `tests/m33-uninstall.test.mjs` — run against a fixture directory structure (not the real `~/.local/bin`), asserts default mode leaves settings/sessions untouched, `--purge` removes them, npm-install and dev-link install types print guidance instead of deleting anything they don't own.
Acceptance: uninstalling a fixture standalone-binary install leaves zero files behind (verified by directory listing before/after); uninstalling a fixture npm install does not attempt to invoke `npm` (explicit no-child-process-spawned assertion, matching Task 12.9's equivalent guarantee for `update`).
Failure modes: running `uninstall` on a dev-link install must not delete the linked *repository* (only the wrapper script + marker) — this is the one place a scope mistake would be genuinely destructive to a maintainer's actual work, so it gets its own explicit test.

**Task 7.21 — `upstage mcp add/remove` (P2, safe surgical merge)**
*P2.* Rationale: explicit follow-up request, scoped against a confirmed real risk (§7.21) rather than a naive parse/stringify implementation.
Dependencies: 12.1 (router); Task 12.4 (`mcp list/status/test/show`, for the config-loading primitives to extend).
Files: NEW `src/tools/mcp/config-writer.mjs` (the surgical text-edit logic, kept separate from `config.mjs`'s read-only loading); MODIFY `src/cli/commands/mcp.mjs` (add `add`/`remove` subcommands).
Contract: `addMcpServer({cwd, name, command, args, env, scope})` and `removeMcpServer({cwd, name, scope})`, both operating on the raw file text (not a parsed-then-restringified object) and writing via temp-file + atomic rename.
Tests: `tests/m33-mcp-config-writer.test.mjs` — the critical test constructs a `.mcp.json` fixture with **multiple existing servers including one with an env var placeholder** (`"${SOME_TOKEN}"`), adds a new server, and asserts every other server's raw text (including the placeholder, unexpanded) is byte-for-byte unchanged; same test repeated for `remove`.
Acceptance: the byte-for-byte-unchanged test above passes; `--scope user` never writes to `.mcp.json`; a malformed/corrupt existing `.mcp.json` is detected and refused (clear error) rather than partially overwritten.
Failure modes: this is the task in the whole plan most likely to be harder than it looks — if a byte-for-byte-preserving text edit proves impractical within scope, the correct fallback is to ship `add`/`remove` only for the case of an **empty or upstage-cli-only-managed** `.mcp.json` (detect and refuse to touch a file with foreign entries) rather than risk corrupting a shared config; document that fallback decision here if taken, don't silently ship the risky version.

**Task 7.22 — `upstage plugins install <source>` (P2, minimal marketplace)**
*P2.* Dependencies: 12.1 (router); `PluginLoader` (existing, for the search-dir target).
Files: NEW `src/cli/commands/plugins-install.mjs`; MODIFY `src/plugins/loader.mjs` if a new search dir (`~/.upstage/plugins/`) needs adding to `SEARCH_DIRS`.
Contract: `installPlugin({source, cwd})` — `source` is a git URL (shells out to `git clone`) or a local path (copies); lands at `~/.upstage/plugins/<derived-name>/`. `updatePlugin({name})`/`updatePlugin({all:true})` re-pulls (`git pull` for git-sourced, re-copy for path-sourced — track which in a small marker file per installed plugin).
Tests: `tests/m33-plugins-install.test.mjs` — install from a local-path fixture (avoid a real network `git clone` in the test suite, per this repo's offline-test-by-default convention, §10), asserts the plugin is then discoverable by `PluginLoader`.
Acceptance: an installed plugin's hooks/MCP servers/agents/skills are loaded on next `upstage` startup, same as a manually-placed plugin today (no special-casing in the loader beyond the new search dir).
Failure modes: installing from an untrusted git URL runs arbitrary code once the plugin loads (stated explicitly in §8) — this task's help text and any confirmation prompt must say so; do not silently auto-load a freshly-installed plugin without at least printing what it's about to run (hooks especially).

**Task 7.23 — `upstage migrate` (P2)**
*P2.* Dependencies: Task 7.20 (uninstall), 7.N/12.9 (install-type detection) — must exist first, this task composes them.
Files: NEW `src/cli/commands/migrate.mjs`.
Contract: `migrateInstall({to: "standalone"|"npm", removeOld})` — detects current install type (dev-link marker checked first, per the failure-mode note already in Task 12.9), performs the target install (reusing the installer's own download/verify logic for `standalone`, printing npm guidance for `npm` per Task 12.9's existing "don't invoke npm ourselves" rule), then either prompts to remove the old install or does so automatically if `--remove-old` was passed.
Tests: `tests/m33-migrate.test.mjs` — covers all three source install types migrating to standalone, asserts the old install is flagged/removed per the flag, and specifically asserts no scenario leaves two `upstage` binaries resolvable on `$PATH` simultaneously after a `--remove-old` run (the exact bug found in Claude Code's issue tracker).
Acceptance: a fixture npm-install → standalone migration with `--remove-old` leaves exactly one resolvable `upstage` on PATH.
Failure modes: same PATH-shadowing bug as the researched precedent if the "remove old" step is skipped or fails silently — this task's tests must fail loudly if that happens, not just check that the new binary was installed.

**Task 7.24 — Small comfort additions (`.upstageignore`, `/bug`, `/model`+`/doctor` consolidation)**
*P2.* Dependencies: `/model` piece depends on Task 7.16; `/doctor` piece depends on Task 12.3.
Files: NEW `src/agent/ignore-patterns.mjs` (`.upstageignore` parsing, gitignore-syntax); MODIFY `src/tools/builtin/repo-map.mjs`, `src/agent/context-builder.mjs`, `src/indexer/intelligence.mjs` (respect ignore patterns during automatic context loading only); NEW handler in `src/ui/commands.mjs` for `/bug`; MODIFY `/doctor`'s and `/model`'s existing handlers to call Task 12.3's/7.16's shared functions.
Tests: `tests/m33-upstageignore.test.mjs` — the critical test asserts an ignored file's content genuinely never appears in `context-builder.mjs`'s output while still being readable via the `read_file` tool directly (proving the boundary is "automatic context only," not "hidden from the agent entirely"); `tests/m33-bug-command.test.mjs` — asserts the captured file contains recent turns + doctor-equivalent info and that no network call is made.
Acceptance: the ignore-boundary test above passes; `/doctor` and `upstage doctor` produce structurally consistent output (same check names) after consolidation.
Failure modes: an ignore pattern that also happens to match a file the user explicitly asks the agent to read must not block that explicit read — re-confirm this distinction is actually implemented as "affects context loading only," not accidentally wired into the permission engine's read gate.

## 13. Risks / Open Questions

- **Schema-generation endpoint path** (§3, Task 7.4) is genuinely unresolved between two sources and must be live-verified, not guessed, before shipping.
- **Groundedness response label enum** (§3, Task 7.6) — only `"notGrounded"` was directly observed; `"grounded"`/`"notSure"` are inferred, not confirmed.
- **Extraction schema property/char-limit numbers** (§3) vary between two fetches of the same reference — treat the smaller (safer) number as the client-side validation ceiling until live-verified.
- **`solar-pro4`'s `reasoning_effort` enum** is richer in Upstage's current reference (`none|minimal|low|medium|high|xhigh|max`) than this repo's current `VALID_REASONING_EFFORTS = {low,high}` (`upstage-adapter.mjs`) — out of scope for 3.2's stated feature list, but flagged here since Task 7.1's live-verification pass will surface it naturally; consider a fast-follow, don't silently expand 3.2's scope to fix it now.
- **`AgentLoader`'s exact public API** wasn't fully confirmed in this audit pass (§2/Task 12.5) — verify before writing the introspection wrapper.
- **Existing on-disk semantic index compatibility** after the embedding-model fix (Task 7.3) — dimension mismatch (1,024 vs. 4,096) needs an explicit rebuild trigger, not a silent wrong-answer failure mode.
- **ACP scope estimate** (§3/§7.K/Task 7.14) is explicitly flagged as possibly optimistic — this is the correct task to descope if the release is at risk, not a hidden assumption.
- **Windows CI coverage** for the two new shell/PowerShell scripts (dev-link, installer) is manual-checklist-level in this plan, not full CI — acceptable for 3.2 per principle 13's "considered explicitly" bar, but a gap a future release could close.
- **`myeolinmalchi/upstage-cli`'s own embedding implementation** (`embedding-query`/`embedding-passage`, claiming 4096-dim) appears to call a stale or nonexistent model — this plan does not attempt to fix or contact that external project, just avoids replicating its bug.
- **`mcp add/remove`'s surgical-edit approach (Task 7.21) is the single highest-implementation-risk task added in this addendum** — the byte-for-byte-preservation requirement is genuinely harder than a naive parse/stringify, and the task's own fallback (refuse to touch a `.mcp.json` with foreign entries) must be taken seriously as a real outcome, not treated as a should-never-happen path.
- **`upstage plugins install` executes third-party code with no sandboxing** (§7.22/§8) — this is a deliberate, stated trust boundary (same as manually placing a plugin directory today), not an oversight, but worth re-confirming the help text/confirmation prompt actually says so before shipping.
- **`.upstageignore`'s boundary (context-loading-only, not a read-access gate)** must be verified by the dedicated test in Task 7.24, not assumed — Claude Code's own `.claudeignore` has had real leak incidents, and this repo has no reason to assume it will get the boundary right on the first attempt without that test.
- **`upstage migrate`'s PATH-shadowing avoidance (Task 7.23)** depends entirely on the "remove old install" step actually running/succeeding — if it silently no-ops, this repo reproduces the exact bug found in Claude Code's issue tracker; the task's test suite is written specifically to catch that, not just to check the new install succeeded.

## 14. Deferred / Explicit Non-goals

Per the requester's explicit exclusion list — not implemented in 3.2, listed here only to explain why:

- **OpenTelemetry exporter / full observability backend integration** — `RuntimeEventBus`'s existing events are already OTel-span-shaped (per the repo's own prior research, §2), making this cheap *whenever* it's picked up, but session export (§7.L) is this release's answer to "get data out of a session" and is a smaller, self-contained substitute for the specific "debug/replay outside the TUI" need.
- **Remote server mode / roaming-agent relay** — real 2026 coding-agent RCE/privilege-escalation CVEs (cited in this repo's own prior research) make opening any network listener on top of a shell-executing agent a decision requiring a dedicated security review pass, not a 3.2-sized feature.
- **Persistent cross-session autonomous memory / Knowledge Items** — no infrastructure gap analysis supports this being small; genuinely a new subsystem.
- **Scheduled tasks / daemon scheduler** — no existing infra to build on; genuinely new.
- **PQC application work** — investigated by this repo's own prior research and found to be a non-issue at current scale (Node's OpenSSL 3.5+ handles it transparently); no new information in this pass changes that conclusion.
- **Full web UI** — contradicts "TUI remains the primary human UI" (principle 8).
- **Remote agent execution** — same CVE-driven caution as remote server mode.
- **Elaborate multi-agent supervisor redesign** — out of scope; this repo's existing subagent dispatch (`run_subagent` tool, worktree isolation) is untouched by this plan.
- **New memory architecture** — out of scope, no gap identified that 3.2's scope requires closing.
- **Generic VCS panel** — not required by anything in this plan's scope (git detection for `doctor`/`version` uses the existing `isGitRepo()` primitive only).
- **Unrelated new agent tools** — this plan deliberately adds **zero** new builtin agent tools (36 stays 36) per principle 9; extraction/classification/schema-gen are CLI-only in 3.2 by design (§7.B–H).
- **Random feature parity work** — every feature in this plan traces to either an explicit prompt requirement or a concrete gap found in the audit (§2/§4); nothing was added "because a neighboring system has it."

## 15. Release Acceptance Criteria

3.2.0 is ready to ship when:

1. `src/upstage/*.mjs` exists and is the sole HTTP-calling code for Document Parse/OCR, Extraction, Schema Generation, Classification, Embeddings, and Groundedness — verified by the grep-based acceptance criteria in Tasks 7.1–7.6 (no remaining `node:https`/duplicate-`fetch` Upstage calls outside `src/upstage/` and `src/model/upstage-adapter.mjs`'s chat-completions path).
2. `read_document`, `semantic_search`, `check_groundedness`, and `src/retriever/providers/upstage.mjs` all have passing tests for the first time (§10).
3. `upstage parse|ocr|extract|schema|classify|embed|groundedness` all work standalone (no agent loop), support `--json`, and return the exit codes specified in §6.
4. `upstage doctor`, `upstage doctor --json`, `upstage mcp list`, `upstage tools list`, `upstage skills list`, `upstage agents list`, `upstage plugins list`, `upstage sessions list` all run against this repo's own dev checkout and produce accurate, secret-free output.
5. `upstage init` (and `/init`) produces a real, non-trivial `UPSTAGE.md` for this repo, and re-running it preserves any manually-added content outside the generated markers.
6. `upstage` (no args), `upstage chat`, `upstage tui` are documented as one entry point and CLAUDE.md/README reflect this.
7. A one-time `scripts/dev-link.sh` + `bun install` gets a maintainer to a working `upstage` command against their dev checkout from any directory, detected as `dev-link` by `doctor`/`version --verbose`.
8. `scripts/install.sh` verifies a checksum, supports `UPSTAGE_VERSION`, and does not destructively `rm -rf` before confirming the new install is good.
9. No command in this release prints an API key, MCP secret, or unredacted file content by default anywhere in stdout/stderr, `--json` included — verified by the dedicated secret-leakage tests in §8/§10, not just code review.
10. Every existing pre-3.2 CLI invocation (flags, `ask`, `--bridge-json`, session resume) still behaves identically — verified by the regression tests in Task 12.1's acceptance criteria.
11. `npm run ci` (check + lint + test + test:ui + smoke) passes on the target platform(s) this release is validated on.
12. ACP (§7.K/Task 7.14) either ships with a passing real-SDK interop test, or is explicitly and visibly deferred in the CHANGELOG with the sizing rationale from §3/§13 — not silently dropped.
13. `upstage context`, `upstage models list/info`, `-e`/`--reasoning-effort`, and `upstage completion` (all P1, Tasks 7.15–7.18) work standalone and are documented alongside the other utility commands in §6.
14. `upstage uninstall` (P1, Task 7.20) cleanly removes a fixture standalone install with zero files left behind, and never deletes settings/sessions without `--purge`.
15. Each of `mcp add/remove`, `plugins install`, `migrate`, and the small comfort additions (all P2, Tasks 7.21–7.24) either ships with its task's full acceptance criteria met, or is explicitly deferred in the CHANGELOG — same non-silent-drop bar as ACP, since all four were added by explicit request rather than the original scope and deserve the same visibility if cut.
