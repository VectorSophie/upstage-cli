# upstage-cli 3.3.0 — verification evidence design

## Context

3.2.0 turned upstage-cli into a complete, installable Upstage platform CLI.
It did not change what the *agent* can verify: `src/sandbox/exec.mjs` only
runs commands on the host, there is no browser, and nothing the agent
produces (test output aside) survives as inspectable evidence — session
files (`src/runtime/session.mjs`) store `toolResults`/`appliedPatches` as
plain capped JSON arrays with no binary/artifact concept.

**Thesis:** *see it, run it, prove it* — give the agent a way to execute in
an isolated container, observe a running web app through the browser, and
leave behind evidence (logs, screenshots, container metadata) that a human
or a later verification pass can actually inspect — without inventing a new
execution abstraction, a new browser automation dependency, or vision
capability Solar doesn't have.

**Research basis:** live audit of the 3.2.0 tree (commit `1840c91`, 859/859
tests passing) plus primary-source checks against Chrome DevTools MCP's
README, Bun's open standalone-executable/Playwright issue
(`oven-sh/bun#18749`), Upstage's Solar Pro4 launch materials (text-only, no
vision), Gemini 3.8 Flash's model page (stable, text+image+video+audio+PDF
in / text out), and the MCP protocol version already pinned in this repo
(`2026-07-28` — already current, no MCP work needed). Full findings live in
the session transcript that produced this doc, not reproduced here.

**Owner decisions locked in (2026-09-19):**
1. Browser: hybrid — native CDP tools are the P0 surface; `chrome-devtools-mcp`
   is documented as the optional advanced-debugging path (already fully
   supported by the existing MCP client — zero new code for that half).
2. Vision sidecar ships in 3.3, but is strictly optional and non-blocking:
   no `GEMINI_API_KEY` (or equivalent) → that stage of verification is
   skipped, never fails the run.
3. Docker execution is opt-in, never auto-preferred; an explicit request for
   Docker that can't be satisfied fails closed (no silent local fallback).
4. ACP stays deferred — no code in this repo depends on it, nothing in this
   release's scope is blocked by its absence.
5. `upstage browser install` (Chrome for Testing) is allowed as an explicit,
   separate opt-in command; nothing auto-downloads a browser as a side
   effect of using verification tools.
6. **Evidence storage is general P0 infrastructure**, not a browser
   feature — Docker run output, browser screenshots/console/network
   capture, and vision-sidecar input/output all share one artifact store.

## A. Evidence store (P0 — everything else in this doc writes to it)

**Problem:** nothing produced by a tool call today can be a file. Screenshots,
container stdout captures, or a rendered accessibility snapshot would today
have to be inlined as strings/base64 into `session.toolResults`, which is
already size-capped (`MAX_HISTORY_ITEMS`) precisely because it's meant for
small JSON, not blobs.

**Design:**
- New `src/runtime/artifacts.mjs`: `writeArtifact(sessionId, {kind, ext, data})`
  → writes to `~/.upstage-cli/sessions/<sessionId>/artifacts/<hash>.<ext>`
  (content-addressed by sha256 of `data`, so identical screenshots across
  turns dedupe for free) and returns `{ path, hash, kind, bytes }`.
- Tool results that produce binary/large evidence store the **returned
  metadata object** in `toolResults`, never the bytes. `session.mjs`'s
  existing `MAX_HISTORY_ITEMS` trim logic is untouched — it already assumes
  small entries, and now that assumption is actually true.
- `kind` is a small fixed enum from day one (`"screenshot" | "console-log" |
  "network-log" | "docker-log" | "vision-response"`) — no plugin registry,
  no configurable kind list. Add a kind when a real producer needs it.
- Cleanup: artifacts live and die with the session directory. No separate
  GC job — `uninstall --purge` and existing session pruning already delete
  the session tree wholesale.
- Session export (`upstage sessions export`, 3.2) already redacts tool I/O;
  it needs one addition — when redacting, replace an artifact reference with
  its metadata (kind/hash/size), not the file itself, unless `--include-artifacts`
  is passed.

**Explicitly not built:** no artifact versioning, no cross-session artifact
sharing, no remote/S3-style backend. Local disk under the existing session
root is the only target for 3.3.

## B. Docker-backed execution

**Problem:** `harness/src/sandbox/docker.mjs` (142 lines) is a correct,
already-tested `DockerSandbox` — `--network none` default, `--memory`/`--cpus`
caps, `--read-only` root + scoped `tmpfs`, `--rm`, 3-tier image cache. The
main agent's `src/sandbox/exec.mjs` has no Docker path at all and every
`run_shell`/`run_tests`/`run_linter`/`run_typecheck`/`run_verification` tool
calls it directly.

**Design:**
- Extract a minimal shared interface both backends implement:
  `exec(command, args, { cwd, env, timeoutMs }) → { stdout, stderr, exitCode }`.
  This is exactly what `runSandboxedProcess` already returns and exactly what
  `DockerSandbox.exec()` already returns — no interface redesign needed, just
  a common shape.
- `src/sandbox/local-executor.mjs`: thin wrapper around the existing
  `runSandboxedProcess` (unchanged behavior, just conforms to the shared
  shape).
- `src/sandbox/docker-executor.mjs`: promotes `harness/src/sandbox/docker.mjs`
  verbatim (same security defaults), adapted to the shared interface. The
  harness's own usage is updated to import the promoted module instead of
  keeping a second copy — **one implementation**, not two.
- Selection: opt-in only, via `--sandbox docker` CLI flag / `UPSTAGE_SANDBOX=docker`
  env / per-tool-call sandbox hint from the verification pipeline (thread E).
  Default remains local, unchanged from today.
- **Fail closed:** if `docker` requested and `DockerSandbox.isAvailable()`
  is false, the tool call returns a policy-style error
  (`DOCKER_UNAVAILABLE: docker requested but not reachable — install/start
  Docker or drop --sandbox docker`), never silently executes locally.
- Every existing call site that spawns a process
  (`run-shell.mjs`, `run-tests.mjs`, `run-linter.mjs`, `run-typecheck.mjs`,
  `run-verification.mjs`) is audited during implementation to confirm it goes
  through the shared executor — this is the concrete risk called out in the
  research memo (a call site bypassing the sandbox would silently defeat the
  whole feature).
- Docker run metadata (image, network mode, exit code, duration) is written
  to the evidence store (thread A, `kind: "docker-log"`) alongside stdout/stderr,
  not just returned inline — this is what makes a Docker-verified run
  auditable later, not just "trust me, it ran in a container."

**Testing:** unit tests for executor selection/fail-closed behavior (no live
Docker required, `isAvailable()` is mockable — same pattern the harness tests
already use); one integration test gated behind an env flag (`docker` binary
present) that actually runs a container, mirroring `h6-sandbox-docker.test.mjs`.

## C. Native browser verification (CDP)

**Problem:** no browser tooling exists. The standalone-binary constraint
(`engines.bun`, `bun build --compile` per CLAUDE.md) rules out bundling
Playwright/Puppeteer as a core runtime dependency — `oven-sh/bun#18749`
confirms `playwright-core` still doesn't survive Bun's compile step, open
and unresolved as of this research.

**Design — minimal native CDP client, not a general automation library:**
- `src/browser/cdp-client.mjs`: launches (or attaches to) Chrome via the
  standard `--remote-debugging-port` flag, speaks CDP directly over
  `WebSocket` (built into `bun`/modern Node — no dependency), targeting only
  the domains this feature needs: `Target`, `Page`, `DOM`, `Accessibility`,
  `Input`, `Runtime`, `Network`, `Log`.
- New builtin tools (`src/tools/builtin/browser-*.mjs`), mirroring the grain
  from the research memo:
  - `browser_open(url)` — launches/attaches, navigates.
  - `browser_snapshot()` — returns the **accessibility tree**, not raw HTML.
    This is the default and only observation format for 3.3 — no
    "give me the DOM" escape hatch, so the model never starts generating CSS
    selectors from soup. Refs from the a11y tree are what `browser_click`/
    `browser_type` take as targets.
  - `browser_click(ref)`, `browser_type(ref, text)` — via `Input`, targeting
    a node resolved from the last snapshot's refs.
  - `browser_console()` — drains `Log`/`Runtime.consoleAPICalled` since last
    call, written to the evidence store (`kind: "console-log"`).
  - `browser_screenshot()` — `Page.captureScreenshot`, written to the
    evidence store (`kind: "screenshot"`), tool result carries the path/hash
    only.
  - `browser_close()` — tears down the CDP session. Browser state is
    ephemeral per invocation — no persistent profile/cookies across agent
    runs by default (matches "no persistent browser identities" from the
    non-goals list).
- Chrome discovery: look for an existing Chrome/Chromium install (standard
  per-OS paths + `PATH`); if none is found, the tool returns a clear error
  naming `upstage browser install` (thread C.1) as the fix — no silent
  no-op, no automatic download.
- `upstage doctor` gains a Chrome-availability check (reachable binary,
  version), consistent with its existing "never fails just because one
  check fails" contract.

**C.1 — optional `upstage browser install`:** a separate, explicitly-invoked
command that downloads Chrome for Testing (per Chrome's own
automation/testing distribution) into `~/.upstage/browser/`. Never invoked
automatically by any verification tool. This satisfies "no giant hidden
downloads unless the user explicitly asks" while still giving CI/headless
environments a one-command path to a working browser.

**C.2 — documented advanced path:** README/`.mcp.json` template note
pointing at `chrome-devtools-mcp` for performance traces and deeper network
inspection than the native tool set covers. No code — the existing MCP
stdio client (`src/tools/mcp/stdio-client.mjs`, protocol `2026-07-28`,
already current) runs it today via a normal `.mcp.json` entry. `upstage init`
can optionally offer to add this entry to a generated `.mcp.json`, same
spirit as its existing `UPSTAGE.md` generation — offered, never forced.

**Explicitly not built:** no Playwright/Puppeteer dependency, no raw-HTML
observation mode, no persistent browser profiles, no multi-tab orchestration
beyond what a single verification flow needs.

## D. Optional vision sidecar

**Problem:** Solar Pro4 is confirmed text-only (Upstage's own Pro4 launch
materials document no image input). A screenshot is only useful as evidence
if something can actually look at it and confirm the app rendered/behaved
correctly.

**Design:**
- Provider-neutral content parts, introduced in the model layer only where
  needed for this feature (not a blanket rewrite of every adapter):
  ```js
  { type: "text", text: "..." }
  { type: "image", source: { type: "file", path: "...", mimeType: "image/png" } }
  ```
- `model-capabilities.mjs` gains `inputModalities`/`outputModalities` arrays
  (e.g. `["text"]` for all three Solar entries today) alongside the existing
  boolean flags — additive, doesn't touch existing fields or callers.
- New builtin tool `inspect_image(path, question)`: resolves an evidence-store
  artifact path, sends it + the question to a capability-selected
  image-input model. `GeminiAdapter` is the only current path with a real
  home for this — bumped off the stale `gemini-2.0-flash` default to
  `gemini-3.8-flash` (current, stable, confirmed image input) as part of
  this work, since shipping a vision tool against a model that's already
  behind is not a reasonable starting point.
- **Strictly optional and non-blocking, per owner decision:** the tool is
  registered only if a usable image-capable adapter is configured (API key
  present). If not configured, the tool is simply absent from the registry —
  the verification pipeline (thread E) treats a missing `inspect_image` tool
  as "skip this stage," never as an error. No key, no tool, no failure.

**Explicitly not built:** no second autonomous agent, no image generation,
no video/audio input despite Gemini 3.8 Flash supporting them — bounded to
"look at this screenshot and answer a question about it."

## E. Wiring it together: the verification pipeline

This is the actual product outcome, not four independent features:

```
edit frontend
  → run_verification (local or --sandbox docker; docker-log artifact on request)
  → browser_open + browser_snapshot/click/type (interact with the running app)
  → browser_console + browser_screenshot (evidence artifacts)
  → inspect_image(screenshot, question)   [only if a vision sidecar is configured — else skipped]
  → final verification result: pass/fail + evidence bundle
     { testOutput, dockerMeta?, browserConsole, screenshot, visionNote? }
```

- `run_verification` (existing tool, `src/tools/builtin/run-verification.mjs`)
  is extended to accept the new evidence references and fold them into its
  existing pass/fail result shape — it does not become a second orchestrator
  that duplicates the agent loop's own tool-calling; the agent still calls
  the individual tools in sequence, `run_verification` is where the final
  bundle is assembled and returned as one structured result.
- Every stage is independently optional: no browser → skip straight to
  test-based verification (today's behavior, unchanged); no Docker → local
  execution (today's behavior, unchanged); no vision key → skip that stage.
  The pipeline degrades gracefully at every step, per the project's existing
  "graceful degradation beats mandatory dependencies" taste constraint.
